# BondKeeper — issuers и securities: разбор полей по итогам сидирования

Свод по переписке о первом прогоне `seed_market.php` / `seed_bondization.php`. Все выводы про ISS API проверены по официальной документации Мосбиржи и реальным примерам ответов, а не по памяти — там, где проверить не удалось, это отмечено отдельно.

## Таблица `issuers`

### ogrn

**Проблема.** У всех эмитентов пусто поле `ogrn`.

**Решение.** ISS API Мосбиржи ОГРН не отдаёт вообще — ни через `/iss/securities.json?q=...` (тот же запрос, что уже даёт `emitent_inn`/`emitent_title`), ни через справочные эндпоинты по бумаге. Это не пробел импортёра, а факт про сам источник.

Смысл добавлять есть: ИНН эмитента при реорганизации может смениться (живой пример из ваших же заметок — Нэппи Клаб, ООО→АО), а ОГРН — более устойчивый идентификатор для будущей сверки с e-disclosure, арбитражными делами, банкротными реестрами. Плюс это стандартный реквизит юрлица, который инвестор ожидает видеть.

Источник — DaData, метод «Организация по ИНН» (`POST https://suggestions.dadata.ru/suggestions/api/4_1/rs/findById/party`, `{"query": "<ИНН>"}`). Бесплатно до 10 000 запросов/сутки — с запасом хватает на разовое обогащение 495 эмитентов и редкие дозаполнения. Прямого бесплатного API у самой ФНС для одиночных запросов сейчас нет (доступ к сырому ЕГРЮЛ ограничили в 2022 году), поэтому практичный путь — через агрегатора, построенного на официальных данных ФНС.

У 2 эмитентов (ирландские SPV — RZD Capital P.L.C., SUEK Securities DAC) ОГРН не будет никогда — как и ИНН, это корректный `NULL`, а не пробел.

**Действие.** Требуется прогнать batch-обогащение. Скрипт уже готов и передан отдельно: `bin/enrich_issuers_dadata.php` + `src/DaData/DaDataClient.php` + `src/DaData/IssuerEnricher.php` (проверен `php -l`, живой вызов API не тестировался — нет ключа и сети из моей песочницы). Нужно: 1) зарегистрироваться на dadata.ru и получить ключ, 2) прогнать `--dry-run --limit=5` для проверки, 3) прогнать боевой запуск.

### full_name / short_name

**Проблема.** `full_name` всегда совпадает с `short_name`.

**Решение.** Причина техническая, не баг: эндпоинт `/iss/securities.json?q=...`, который вы используете для identity эмитента, отдаёт **только одно** текстовое поле имени — `emitent_title`. У самих бумаг (securities) в ISS отдельно есть `NAME`/`SHORTNAME`, а вот у эмитента в этом же общем поиске второго, «краткого» варианта не существует. Импортёр не ошибается — он кладёт единственное доступное значение в оба поля.

Тот же самый вызов DaData, который закрывает ОГРН и ОКВЭД (см. ниже), возвращает и полное, и краткое наименование раздельно, из ЕГРЮЛ: `data.name.full_with_opf` («Публичное акционерное общество…») и `data.name.short_with_opf` («ПАО …») — реально разные строки, не дубликат.

**Действие.** Опционально, тем же прогоном `bin/enrich_issuers_dadata.php` (флаг обновления имён включён по умолчанию, отключается `--no-names`). Если разница full/short не используется в продукте прямо сейчас — можно не спешить, ничего не блокирует.

### okved

**Проблема.** Данных по ОКВЭД нет вообще.

**Решение.** Тоже отсутствует в ISS API — тот же список подтверждённых/неподтверждённых полей, что и по ОГРН. Смысл добавлять умеренный: не критично для мониторинга событий по бумагам, но полезно для секторальной аналитики (риск-кластеры по отрасли, фильтры вида «все девелоперы», «все МФО»). Раз DaData всё равно дёргается ради ОГРН — ОКВЭД (`data.okved`, основной код) приходит в том же самом ответе бесплатно, отдельного смысла тянуть его порознь нет.

**Действие.** Закрывается тем же прогоном `bin/enrich_issuers_dadata.php`, что и ОГРН — отдельных действий не требуется.

## Таблица `securities`

### Уровень листинга (`listing_level`)

**Проблема.** Непонятно, на что влияет и как определяется.

**Решение.** Поле `LISTLEVEL` уже приходит в `/iss/securities/{SECID}` — вы его уже получаете. Определяется не формулой, а прохождением эмитентом критериев Правил листинга Мосбиржи: для Первого уровня — по сути, минимальный кредитный рейтинг эмитента/выпуска либо прямой/косвенный госконтроль; для Третьего — требования минимальны, туда обычно и попадают новые ВДО-выпуски, а некоторые категории эмитентов (например, МФО) выше Третьего уровня подняться не могут в принципе.

На что влияет практически:
- ниже определённого уровня доступ для неквалифицированных инвесторов может требовать теста у брокера или статуса квала (отдельно от вашего `ISQUALIFIEDINVESTORS`, но коррелирует);
- при полном дефолте биржа кросс-делистит все бумаги эмитента из 1/2 уровня в течение 2 торговых дней;
- неформально рынок использует уровень как быстрый прокси надёжности.

**Действие.** Не требуется — вопрос был теоретический, данные уже загружаются, поле рабочее.

### initial_issue_volume

**Проблема.** Непонятно, деньги это или штуки.

**Решение.** Штуки. По официальной спецификации ISS: `ISSUE_SIZE` — «Объём выпуска, в штуках ценных бумаг» (Issue volume, number of securities), подтверждено и живым примером (`ISSUESIZE="21586948000"` у SBER — явно не рубли). Если нужен объём в деньгах — это `ISSUESIZE × FACEVALUE` (или `× INITIALFACEVALUE`, если важен объём именно на момент размещения, до амортизации).

**Действие.** Нужно явно решить и задокументировать семантику колонки. Если по названию колонки (`initial_issue_volume`) подразумеваются деньги, а туда пишутся штуки — это надо поправить в коде импортёра (домножить на номинал) или переименовать колонку, чтобы не заложить баг в будущие расчёты.

### trading_start_date

**Проблема.** Данных нет вообще.

**Решение.** Данные, скорее всего, есть — просто не вытаскиваются. В том же `/iss/securities/{SECID}` описании, которое вы уже парсите, подтверждены живыми примерами два поля: `ISSUEDATE` («Дата начала торгов») и `STARTDATEMOEX` («Дата начала торгов на Московской Бирже») — на примере облигации Магнита оба показывают одну и ту же дату. Это та же история, что раньше была с ИНН эмитента: поле физически в ответе есть, просто не читается кодом.

**Действие.** Проверить сырой JSON, который уже получает `SecuritiesImporter`, и добавить чтение `ISSUEDATE`/`STARTDATEMOEX` в парсинг. Новый API-запрос не нужен.

### has_offer

**Проблема.** Данных нет вообще.

**Решение.** Прямого булева поля «есть оферта» нет, но выводится из двух разных полей — важно не путать их источник:
- `BUYBACKDATE` — в блоке `description` `/iss/securities/{SECID}.json`, том же, что уже даёт `MATDATE`/`LISTLEVEL`/`ISSUESIZE`;
- `OFFERDATE` — добавлено в 2017 году **отдельно**, в блок SECURITIES доска-специфичных запросов (`/iss/engines/stock/markets/bonds/boards/{BOARD}/securities/...`) и в исторические аналоги — не та же самая, что description-эндпоинт. Раз вы уже ходите в этот endpoint за `COUPONVALUE`/`NEXTCOUPON`/`ACCRUEDINT` (рыночные данные), `OFFERDATE`, скорее всего, уже приходит в этом же ответе.

`has_offer = (BUYBACKDATE IS NOT NULL OR OFFERDATE IS NOT NULL)` — рабочая гипотеза, не проверенная живьём на бумаге с заведомо активной офертой.

**Действие.** 1) Добавить чтение `OFFERDATE` из уже вызываемого доска-эндпоинта. 2) Протестировать оба поля на бумаге с реальной активной офертой — не факт, что они всегда синхронны. 3) Только после этого закладывать логику `has_offer` в код.

### security_type

**Проблема.** Данных нет вообще.

**Решение.** Похоже на ту же историю, что и с `trading_start_date`. В общем поиске `/iss/securities.json?q=...` — том самом эндпоинте, который уже используется для `emitent_inn`/`emitent_title` — есть столбец `type` (для облигаций принимает значения вида `corporate_bond`, `ofz_bond`, `subfederal_bond`, `municipal_bond`, `exchange_bond`, `cb_bond`, `euro_bond`, `ifi_bond`) и `group` (`stock_bonds` и т.п.). Проверка на бумаге-акции показала эти поля в description-блоке, но на бумаге-облигации (Магнит) в аналогичном примере их не было видно — так что достоверно подтверждён только общий поиск `securities.json?q=`, а не единичный description-эндпоинт.

Отдельная важная находка не по прямому вопросу, но по смежному (`coupon_type`, `is_structured`): с 8 декабря 2025 года Мосбиржа ввела в биржевой шлюзовой протокол (ASTS Bridge, для профессиональных терминалов) новую структурированную классификацию — таблицы `BONDTYPE` («Вид облигации») и `BONDSUBTYPE` («Подвид облигации»), обе как числовой код с расшифровкой в отдельном справочнике, плюс Z-спред, который биржа теперь считает сама ежедневно для всех облигаций, кроме структурных. Формулировки, которые вы цитировали как значения `BOND_TYPE» («Фикс с известным купоном», «Амортизируемые облигации», «Структурная облигация») очень похожи на текст поля `DESCRIPTION` именно этого нового справочника — то есть у вас, вероятно, есть только `BONDTYPE`, а `BONDSUBTYPE` (более узкий уровень) не читается вовсе. **Не подтверждено**, зеркалит ли бесплатный публичный ISS REST API эти новые поля один в один — подтверждено только их существование в шлюзовом протоколе.

**Действие.** 1) Проверить сырой ответ `/iss/securities.json?q=` на предмет полей `type`/`group` — велика вероятность, что уже приходят. 2) Отдельным запросом проверить любую облигацию на предмет полей `BONDTYPE`/`BONDSUBTYPE`/`ZSPREAD` в JSON — если они там есть, это готовая структурированная классификация вместо текстового угадывания по ключевым словам, причём разом для нескольких открытых вопросов.

### is_high_yield (ВДО)

**Проблема.** Данных нет, непонятно, стоит ли добавлять и откуда брать.

**Решение.** Юридически статуса «ВДО» не существует — понятие не закреплено в законах РФ, поэтому в ISS его тоже нет. Рыночный консенсус по критериям: ставка купона/доходность выше ключевой ставки ЦБ на 5 п.п. и более, небольшой объём выпуска, низкий рейтинг эмитента или его отсутствие.

Смысл добавлять есть — прямое попадание в целевую аудиторию продукта. Два бесплатных варианта:
- **Расчёт по формуле.** У вас уже есть купон/доходность и объём выпуска (`ISSUESIZE`) — не хватает истории ключевой ставки ЦБ, а это маленький, редко меняющийся, полностью открытый справочник (публикуется Банком России, несколько значений в год).
- **Сверка с готовым индексом MOEX** — обычные ISS-эндпоинты, без авторизации. Найдены точные тикеры: `RUCBHYTR` (Индекс ВДО-ПИР), `RUEYBCSTR` (Индекс облигаций повышенной доходности), `RUGROWTR` (Индекс Сектора роста, более мягкий критерий). Состав на дату:
  ```
  GET /iss/statistics/engines/stock/markets/index/analytics/RUCBHYTR/tickers.json
  ```

Точнее всего станет, когда появятся кредитные рейтинги (третий критерий) — вы это и так планируете отдельным модулем.

**Действие.** Решить, какой из двух вариантов брать за основу (или оба). Не реализовано — требует отдельной разработки: либо мини-таблица `key_rate_history` + формула, либо периодическая сверка с составом индекса.

### coupon_type = unknown

**Проблема.** Часть бумаг имеет статус `unknown`; непонятно, почему не только структурные облигации.

**Решение.** Механизм — поиск ключевых слов в свободнотекстовом `BOND_TYPE` (`fixed` ставится только при явном совпадении). Поэтому в `unknown` попадают не только структурные облигации, а любая бумага, чей `BOND_TYPE` описывает не характер ставки, а что-то другое — валюту номинала, амортизационную структуру, ипотечную природу — даже если купон на самом деле обычный фиксированный. Отдельная вероятная категория — ступенчатый купон (заранее известный, но по расписанию меняющийся): скорее всего, в `BOND_TYPE` нет слова «фикс», и такие бумаги тоже проваливаются в `unknown`, хотя это отдельный четвёртый тип, а не «неизвестно».

См. также находку про `BONDSUBTYPE` в разделе `security_type` выше — вероятно, вы читаете только верхний уровень классификации (`BONDTYPE`), а более узкий (`BONDSUBTYPE`) вообще не используете, и именно там может быть прямой признак характера ставки.

**Действие.** Прогнать диагностику и разобрать по факту:
```sql
SELECT BOND_TYPE, COUNT(*) 
FROM securities 
WHERE coupon_type = 'unknown' 
GROUP BY BOND_TYPE 
ORDER BY COUNT(*) DESC;
```
По результату — расширить словарь ключевых слов, завести `coupon_type = 'step'`, либо признать часть действительно неопределяемой без чтения проспекта. Плюс проверить наличие `BONDSUBTYPE` в сыром ответе ISS (см. выше).

### coupon_type = zero_coupon

**Проблема.** Непонятен смысл статуса.

**Решение.** Облигация без периодических купонных выплат вообще — доход инвестора формируется только за счёт покупки ниже номинала и погашения по номиналу (дисконтная облигация). На российском корпоративном рынке редкость, встречается в основном у коротких «коммерческих облигаций». В вашей реализации значение, вероятно, ставится не по ключевому слову в `BOND_TYPE`, а по факту — bondization-эндпоинт возвращает пустой массив `coupons`.

**Действие.** Не требуется — это разъяснение термина, а не проблема. Стоит только явно свериться в коде `BondizationImporter`, что логика именно фактическая (пустой массив купонов), а не текстовая — это важно для следующего пункта (`coupon_frequency`).

### coupon_frequency = NULL

**Проблема.** У части бумаг `coupon_frequency` не заполнен; первая гипотеза (это только zero_coupon бумаги) не подтвердилась на реальных данных — таких бумаг всего 2, номинал есть у всех бумаг без исключения, а отсутствие `MATDATE` не коррелирует с NULL.

**Решение.** Пересмотренная гипотеза: `FACEVALUE` берётся из статичного description-эндпоинта, не зависящего от активности торгов, а `COUPONFREQUENCY`, по всей видимости, приходит из доска-специфичного securities/marketdata-блока (тот же источник, что и `OFFERDATE`, см. `has_offer` выше) — то есть требует, чтобы у бумаги была текущая активная торговая доска. Тогда NULL должен коррелировать не с отсутствием `MATDATE`, а с тем, что `MATDATE` уже в прошлом (бумага погашена, доска неактивна) — это разные проверки, и вторая ещё не делалась.

**Действие.** Прогнать уточнённую диагностику:
```sql
SELECT 
  CASE WHEN mat_date < CURDATE() THEN 'уже погашена' ELSE 'ещё торгуется' END AS bucket,
  COUNT(*) 
FROM securities 
WHERE coupon_frequency IS NULL 
GROUP BY bucket;
```
Если основная масса — «уже погашена», гипотеза подтверждается, это архивные бумаги без активной рыночной строки, а не баг. Если нет — второй разрез: по `is_structured`/`BONDSUBTYPE` (структурные облигации явно исключены биржей из расчёта Z-спреда, вероятно и по частоте купона у них своя логика). Вопрос остаётся открытым до результата запроса.

### is_subordinated

**Проблема.** Данных нет вообще.

**Решение.** Подтверждённо отсутствует в ISS API. Субординированные облигации в России выпускают почти исключительно банки (Положение Банка России №646-П, ст. 25.1 ФЗ «О банках и банковской деятельности») — узкое, легко очерчиваемое множество, не задача для всех 495 эмитентов. Единого бесплатного машиночитаемого реестра суборд-выпусков не нашлось — ни у ЦБ, ни у Cbonds/RusBonds в открытом виде; каждый банк публикует список своих суборд-выпусков на собственном сайте раскрытия.

**Действие.**
1. Отфильтровать кандидатов по банковскому ОКВЭД (64.x) — после того как ОКВЭД подтянется через DaData (см. `issuers` выше).
2. В этой узкой выборке проверить `BOND_TYPE` на подстроку «субординир» (тот же метод, что дал `is_structured`).
3. Косвенно перепроверить по признакам: бессрочность (нет `MATDATE`), аномально высокая текущая доходность.
4. Для итоговой сверки — вручную по 5–10 крупным банкам (Альфа-Банк, Сбербанк, Т-Технологии, ВТБ и т.п.), сверяясь с их страницами раскрытия. Для вашего масштаба это реалистично сделать за один присест без автоматизации.

### floater_base_rate / floater_spread_percent / floater_formula_note

**Проблема.** Данных нет вообще по всем трём полям. Уточнение по смыслу полей: `floater_base_rate` — уже посчитанное числовое значение базы на релевантную дату (не название индекса), `floater_spread_percent` — числовой спред (условно +2%), `floater_formula_note` — текстовое описание для сложных/нестандартных случаев.

**Решение.** Подтверждённо недоступны структурно через ISS API — bondization-эндпоинт отдаёт только уже наступившие, зафиксированные купоны (`valueprc`), а не формулу будущих. Найдены три пути, по убыванию готовности:

1. **floaters.ru** — рабочий, бесплатный, живой источник: таблица на несколько сотен выпусков в формате «КС + 1.25%12 в год» / «RUONIA + 1.9%4 в год» — то есть база, спред числом и частота в одной строке, плюс ISIN. Это не JSON-API, а HTML-страница (сайт на Next.js, возможен скрытый внутренний JSON-эндпоинт — стоит проверить через вкладку Network в браузере до парсинга HTML). Перед автоматическим сбором — свериться с `robots.txt` и, при желании, написать авторам в их телеграм-канал (t.me/floaters_ru).
2. **Собственный расчёт `floater_base_rate` как числа** — ключевая ставка и RUONIA публикуются ЦБ бесплатно (ключевая — несколько значений в год, RUONIA — ежедневно). Отдельно найдены в ISS `CBRCLOSE` («вменённая ключевая ставка ЦБ») и `IRICPICLOSE` («вменённая RUONIA») в блоке marketdata — не проверено, подходят ли они как прямой источник числа для `floater_base_rate`, или это рыночно-оценочные метрики другого назначения. Также стоит проверить, не является ли уже упомянутый Z-спред (новое поле MOEX с декабря 2025, см. `security_type` выше) готовым прямым источником для `floater_spread_percent`.
3. **bondana.app/web** — не удалось проверить содержимое: страница отдаёт пустой HTML-каркас, рендерится в браузере через JS.

**Действие.** Не реализовано, требует решения по подходу. Рекомендация: начать с парсинга floaters.ru (после проверки его технических условий) как самого быстрого пути к структурным `base_rate`/`spread`, при неудаче — собственный расчёт по ключевой ставке/RUONIA. `floater_formula_note` в любом случае можно заполнять сырым текстом формулы уже сейчас, без ожидания решения по первым двум полям.

### offer_type (put/call, «вид оферты»)

**Проблема.** Данных нет вообще.

**Решение.** В ISS API поля нет — есть похожее по названию поле `offertype` в объекте `Offer` bondization-эндпоинта, но это **статус события оферты** («Оферта», «Оферта (состоялось)», «Оферта (отменено)», «Оферта (дефолт)», «Оферта (технический дефолт)»), а не тип put/call — важно не перепутать. Бесплатный структурированный источник за пределами ISS не найден. Единственный подтверждённый вариант — RusBonds: на карточке конкретной бумаги, вкладка «Выкуп», прямо указано «безотзывная» (put) или «отзывная» (call) с условиями досрочного погашения. Это HTML-страница на ISIN, не API — RusBonds коммерческий провайдер, автоматический сбор стоит сверить с их пользовательским соглашением перед реализацией.

Рыночная эвристика на случай, если точных данных нет: put-оферта — основная форма на российском рынке, call — реже, в основном у банковских и субординированных выпусков (то самое узкое пересечение с `is_subordinated` выше).

**Действие.** Для бумаг с активной офертой — смотреть вручную вкладку «Выкуп» на RusBonds по конкретным ISIN (их не тысячи одновременно). Автоматизация возможна только после проверки условий использования RusBonds. Как временный дефолт без похода по карточкам — `offer_type = 'put'`, кроме кандидатов в `is_subordinated`, с пометкой «требует проверки».

### status

**Проблема.** Непонятно, считается ли поле самостоятельно.

**Решение.** Да, и это осознанное архитектурное решение, а не пробел — единого ISS-поля для жизненного цикла бумаги (активна/погашена/дефолт/делистинг) нет. Собирается из нескольких сигналов самостоятельно: `MATDATE`, флаг активности из общего каталога `/iss/securities.json`, собственная событийная логика по дефолтам. Подтверждает то, что уже зафиксировано в вашем README («issuers/securities физически не удаляются — см. status-поле»).

Отдельная находка не по прямому вопросу: в официальной спецификации полей есть `DEFAULT_STATE` — «В стадии технического дефолта по неисполнению обязательств? (Y/N)» — потенциально прямой структурированный сигнал для основной функции продукта. Не проверено на бумаге, реально находящейся в техдефолте.

**Действие.** Базовая логика не требует действий — вопрос закрыт. Отдельно стоит проверить `DEFAULT_STATE` на реальном техдефолтном ISIN — если поле рабочее, это может ускорить событийный детектор дефолтов, который всё равно в планах.

## Особый случай: ипотечные ценные бумаги (ИЦБ) — пример ДОМ.РФ обл. сер. А15

**Проблема.** По бумаге RU000A0JQAM6 (ДОМ.РФ, серия А15) не выгрузилась полная история купонов в таблице `coupons`.

**Решение.** Это не баг импорта, а структурная особенность самой бумаги. RU000A0JQAM6 — ИЦБ (ипотечная ценная бумага), выпущена через SPV «ДОМ.РФ Ипотечный агент», а не обычная корпоративная облигация. При переменном доходе ставка купона не фиксируется заранее: инвестору выплачивается сумма процентных поступлений по закладным, реально полученных за отчётный период, за вычетом расходов агента. Частичное погашение номинала — в те же даты, в размере фактических поступлений по погашению основного долга; сам номинал равен остатку долга по пулу закладных.

Следствие: у ISS физически не может быть «полного графика вперёд» для этой бумаги — будущие суммы не существуют как числа до тех пор, пока реальные заёмщики не заплатят по своим ипотекам за соответствующий период. Это не пробел биржи и не ваш баг, а то, как физически устроен инструмент. Тот же принцип, вероятно, касается и всей категории ипотечных бумаг ДОМ.РФ, которую вы уже видели как отдельный тег в `BOND_TYPE`.

**Действие.**
1. Проверить, что именно отсутствует: если пропуски только в будущем — это ожидаемо, действий не требуется. Если пропуски есть и в прошлом (уже прошедшие купонные даты без данных) — это отдельный, реальный повод для разбора.
2. Дозаполнение произойдёт естественным образом при повторных прогонах `seed_bondization.php` — прошедшие периоды будут постепенно появляться по мере публикации биржей уже случившихся сумм; полного графика вперёд не будет никогда, это ожидаемое поведение, а не то, что нужно «чинить».
3. Стоит завести отдельный флаг (например, `is_mortgage_backed`) по тегу «ипотечные» в `BOND_TYPE` или по имени эмитента (`%Ипотечный агент%`), чтобы в продукте не показывать пользователю пустой/сломанный на вид график там, где его структурно не существует.
4. Для этой категории `floater_base_rate`/`floater_spread_percent`, скорее всего, не применимы — нет индекса и спреда в привычном смысле; описание вида «доход = поступления по закладным минус расходы агента» логично класть в `floater_formula_note` текстом.

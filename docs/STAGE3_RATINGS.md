# Этап 3 — рейтинги агентств: журнал решений

Цель этапа: наполнить `current_ratings` (текущий рейтинг по паре
эмитент/агентство) и, следующим шагом, `rating_actions` (история
рейтинговых действий — новости/пресс-релизы). Источники — публичные
страницы 4 агентств, аккредитованных ЦБ (https://www.cbr.ru/finm_infrastructure/ra/):
«Эксперт РА», АКРА, НРА, НКР. Ни у одного нет открытого API — только
HTML-страницы (и у двух из четырёх — кнопка выгрузки в Excel).

**Первый шаг (по прямому указанию пользователя) — только `current_ratings`,
только с "текущих рейтингов" на сайтах агентств.** Парсинг новостей/
пресс-релизов (для `rating_actions`) — следующая, отдельная задача.

## Схема (миграция 013)

`rating_actions`/`current_ratings` уже были заложены в `001_schema.sql`,
но не совпадали с уточнённой пользователем спецификацией в трёх местах:

1. **`outlook` → `outlook_from` + `outlook_to`.** Было одно поле
   "прогноз после действия". Пользователь явно попросил хранить и
   прогноз ДО — по аналогии с уже существующей парой `rating_from`/
   `rating_to`. Переименовали существующую колонку в `outlook_to`,
   добавили `outlook_from` рядом.
2. **`review_type` получил `DEFAULT 'scheduled'`.** Пока парсинг не умеет
   отличать плановое рейтинговое действие от внепланового, пользователь
   попросил дефолт `'scheduled'` везде — большинство реальных действий на
   практике плановые.
3. **`current_ratings.created_at` — новая колонка.** Раньше было только
   `updated_at` (с `ON UPDATE`). Пользователь разделил семантику: `created_at` —
   когда строка появилась, `updated_at` — когда обновлялась в последний
   раз (обычно совпадает с `last_action_date`, но не обязано).

`current_ratings` остаётся с составным `PRIMARY KEY (issuer_id, agency)` —
это уже было в `001_schema.sql` и явно устраивает пользователя (не
попросил добавить суррогатный `id`).

## Источники — что подтвердил пользователь по каждому агентству

| Агентство | Код (`agency`) | Текущие рейтинги | Новости/пресс-релизы |
|---|---|---|---|
| Эксперт РА | `expert_ra` | https://raexpert.ru/ratings/ | https://raexpert.ru/news/ |
| АКРА | `acra` | https://www.acra-ratings.ru/ratings/issuers/ | https://www.acra-ratings.ru/press-releases/ |
| НРА | `nra` | https://www.ra-national.ru/ratings/ (есть Excel-выгрузка) | https://www.ra-national.ru/news/ |
| НКР | `nkr` | https://ratings.ru/ratings/issuers/ (есть Excel-выгрузка) | https://ratings.ru/ratings/press-releases/ (актуальнее) и https://ratings.ru/news/ |

У каждого агентства свой движок сайта — общего парсера не будет, под
каждое нужен свой разбор. Все 4 не защищены капчей/анти-бот системой
(в отличие от service.nalog.ru, см. работу над `fns_blocks`) — это
обычные публичные страницы, разбор которых не требует обхода защиты.

## Самый рискованный момент — сопоставление компании с `issuers.id`

Задал пользователю прямой вопрос: показывают ли страницы/выгрузки ИНН
рядом с рейтингом. Ответ:

- **На странице списка рейтингов (и в новостях) — только название
  компании**, без ИНН/ОГРН рядом со строкой рейтинга.
- **У каждой компании есть отдельная карточка** (пример:
  `https://raexpert.ru/database/companies/raiffaizenbank_avstriya/`),
  и **не у всех компаний** в карточке показан ИНН (пример карточки без
  ИНН: `https://raexpert.ru/database/regions/sakha/` — впрочем, это
  карточка региона, не компании; нужно будет отдельно проверить карточку
  реальной компании без ИНН, когда такая найдётся).

**Из этого следует стратегия сопоставления (предварительная, до того как
увидим реальные карточки в достаточном количестве):**
1. Основной путь — нормализованное сопоставление по названию
   (`issuers.full_name`/`short_name`): убрать организационно-правовую
   форму (ООО/АО/ПАО/...), кавычки, лишние пробелы, привести к одному
   регистру.
2. Там, где сопоставление по названию неоднозначно (несколько кандидатов
   или ни одного уверенного совпадения) и карточка компании на сайте
   агентства показывает ИНН — переходить по ссылке на карточку и сверяться
   по ИНН.
3. **Если ни то, ни другое не даёт уверенного результата — строка НЕ
   записывается в `current_ratings`, а попадает в отчёт "не сопоставлено"
   (тот же принцип, что уже есть в `SecuritiesImporter`/`FnsBlocksImporter`
   — честно показать пропуск, а не угадать и записать не туда).** Ошибка
   сопоставления здесь хуже, чем в любой другой части проекта: она молча
   приписывает рейтинг/риск не той компании.

Финальная реализация матчера — после того, как увидим реальную структуру
через `bin/debug_rating_page.php` (см. ниже) на настоящих страницах и
поймём, насколько чистые там названия и как часто нужен запасной путь
через ИНН.

## `bin/debug_rating_page.php` — диагностика перед парсером

По тому же принципу, что `bin/debug_iss_security.php` для ISS API:
сначала смотрим на реальный HTML, потом пишем код под него. Скрипт
универсальный (не знает заранее ни про одно агентство) — печатает:
- все `<table>` на странице (число строк, первые 3 строки текстом);
- ссылки, похожие на Excel-выгрузку (`.xlsx`/`.xls`/`export`);
- все вхождения слова "ИНН" с контекстом;
- если таблиц нет — топ-15 самых часто повторяющихся CSS-классов
  (кандидаты на "один класс — одна строка списка", если вёрстка не
  табличная, а через `div`/`li`).

Если ответ не HTML (сама Excel-выгрузка) — сохраняет файл целиком
локально и печатает сигнатуру, дальше смотреть `unzip -l` (xlsx — это
ZIP с XML внутри) отдельно.

**Проверено на синтетической локальной странице (таблица + ссылка на
.xlsx + текст "ИНН компании: ...")** — вся логика (разбор таблицы,
поиск Excel-ссылки, контекст вокруг "ИНН") отрабатывает корректно.
**НЕ проверено на реальных сайтах агентств** — из песочницы разработки
нет исходящего доступа в интернет на произвольные домены (та же
причина, по которой ISS API и service.nalog.ru тоже проверялись только
пользователем на реальном сервере).

**Обновление — пользователь открыл доступ к этим доменам из песочницы,
разведка проведена вживую (август 2026).** Всё ниже — реальные находки,
не предположения.

## Живая разведка — что подтвердилось

**Доступность (через тот же egress-прокси, что и весь остальной трафик
сессии):**
- raexpert.ru, ra-national.ru, ratings.ru — отвечают нормально (HTTP 200).
- **acra-ratings.ru — не открывается.** `acra-ratings.ru` (без www) —
  403 от прокси (нет в списке разрешённых доменов). `www.acra-ratings.ru`
  — проходит через прокси, но у их собственного сервера битая цепочка
  TLS-сертификата (`unable to get local issuer certificate` уже на этапе
  handshake, не на уровне проверки прокси) — это проблема на стороне
  АКРА, а не что-то, что чинится с нашей стороны (инструкции сессии прямо
  запрещают отключать проверку TLS). Нужно решение пользователя: либо
  открыть `acra-ratings.ru` (без www) в списке разрешённых доменов и
  надеяться, что там сертификат в порядке, либо смириться, что АКРА
  пока недоступна с этой машины, либо забирать данные АКРА как-то иначе
  (например, самому пользователю вручную/с другой машины).

**Эксперт РА (raexpert.ru) — ИНН только через карточку компании, страница
списка платная для выгрузки:**
- `/ratings/` — страница СРАЗУ отдаёт HTML-таблицу (`Объект | Рейтинг |
  Прогноз | Обновлен`), без JS-рендеринга. Но по умолчанию показывает ВСЕ
  типы рейтингов вперемешку (компании, регионы, муниципалитеты,
  суверенные, отдельные выпуски облигаций) — нужно фильтровать по
  категории.
- Категории заданы через отдельные пути, например `/ratings/credits/`
  (нефинансовые компании), `/ratings/bankcredit/` (банки),
  `/ratings/credits_holding/` (холдинги), `/ratings/leasing_rel/`
  (лизинг), `/ratings/factor/` (факторинг), `/ratings/mfi_credits/`
  (МФО), `/ratings/insurance/` (страховые) — полный список категорий
  виден в фильтре на `/ratings/` (чекбоксы с `data-path`).
  `/ratings/regioncredit/`, `/ratings/municipalities/`,
  `/ratings/sovereign_ratings/` — субъекты РФ/муниципалитеты/суверен, не
  имеют юрлица-эмитента с ИНН в привычном смысле — вероятно, не наш
  случай.
- **Пагинация — не по URL-параметру, а через сессию:** клик по номеру
  страницы шлёт `POST /ratings/index/ajax-set-rating-page-hash/` с
  непрозрачным хэшем (взят из `onclick` пагинатора на уже загруженной
  странице) и CSRF-токеном (`CSRFAjaxTokenPageHash`, тоже в HTML
  страницы), после чего `GET` того же URL отдаёт уже следующую
  страницу — состояние живёт в cookie-сессии. **Проверено вживую и
  реально работает** (curl с cookie jar): страница 1 и страница 2 дают
  разные наборы компаний.
- **Каждая компания в таблице — ссылка на карточку**
  (`/database/companies/{id или "человеческий" слаг}/`, например
  `/database/companies/1000074252` или
  `/database/companies/raiffaizenbank_avstriya/`). **На карточке — блок
  "Реквизиты" с ИНН, ОГРН, КПП** (проверено на 4 реальных карточках —
  банк, золотодобывающая компания, страховой холдинг: везде ИНН нашёлся).
  Не находится у иностранных юрлиц без российской регистрации (пример:
  "Rissa Investments Limited" — ни ИНН, ни блока "Реквизиты" вообще нет,
  это ожидаемо, не баг).
- **Экспорт в Excel требует авторизации** (`onclick="unauthSubmite()"`
  на кнопке "Экспорт") — тот самый "пиздец допотопный" личный кабинет
  из первого сообщения пользователя. Единственный бесплатный путь без
  логина — краулинг HTML: список (постранично, с cookie-сессией) плюс
  по одному запросу на карточку каждой компании ради ИНН. Масштаб по
  категориям из фильтра: нефинансовые компании 196, банки 146,
  страховые 32, лизинг 33, холдинги 16, МФО 15, финкомпании 29 —
  **порядка 400-500 компаний, то есть примерно столько же HTTP-запросов
  на карточки** (плюс десятки запросов на сами страницы списка). Прежде
  чем запускать такой краулинг на боевом сайте агентства, стоит
  подтвердить с пользователем масштаб/паузы между запросами — то же
  соображение вежливости, что и с service.nalog.ru, только тут в разы
  больше запросов и нет защиты капчей, которая естественно ограничивала
  бы скорость.
- **Импортёр реализован и прогнан вживую целиком** — см. раздел "Эксперт РА — импортёр реализован" ниже.

**НРА (ra-national.ru) — ИНН прямо в Excel-выгрузке, причём выгрузка
содержит ВСЮ историю, а не только текущее состояние:**
- Кнопка "Выгрузить в Excel" на `/ratings/` — прямая, статическая ссылка
  прямо в HTML: `/wp-load.php?security_key=...&export_id=20&action=get_data`
  (ключ читается со страницы каждый раз, не захардкожен — вдруг
  меняется). Один GET — сразу настоящий `.xlsx` (не HTML-заглушка).
- Колонки: `id, Название организации, ИНН, Название пресс-релиза, Дата
  опубликования пресс-релиза, Рейтинг, Статус рейтинга, Прогноз, Вид
  рейтинга, Сектор организации, Отрасль, ОСК, ISIN, Ссылка на пресс
  релиз, Под наблюдением`.
- **935 строк на момент проверки — это вся история рейтинговых действий
  с 2020 года**, не снимок "сейчас". У части компаний по несколько строк
  за разные даты. `current_ratings` строится как "последняя по дате
  строка на эмитента" — реализовано в `NraImporter`.
- **"Вид рейтинга" смешивает кредитные рейтинги эмитента с ESG,
  рейтингами качества услуг (УК/ИК/НПФ/депозитариев/регистраторов) и
  кредитным рейтингом ОТДЕЛЬНЫХ ВЫПУСКОВ ОБЛИГАЦИЙ** (это про
  security_id, не issuer_id — не то, что хранит `current_ratings`).
  Оставлены только 5 значений, которые прямо про кредитоспособность
  самого эмитента: `Кредитный рейтинг нефинансовых компаний`,
  `Кредитный рейтинг кредитных организаций`, `Кредитный рейтинг
  лизинговых компаний`, `Кредитный рейтинг страховых организаций`,
  `Кредитный рейтинг инвестиционно-финансовых компаний`.
- **ИНН хранится в Excel как ЧИСЛО, не текст** — у 2 из 935 строк
  (одна и та же компания дважды) при экспорте потерялся ведущий ноль
  (10 цифр → 9). `IssuerMatcher::normalizeInn()` возвращает один ведущий
  ноль обратно, если после этого длина не 10/12 — считает ИНН
  нераспознанным, не гадает дальше.
- **Открытый вопрос пользователю: раз вся история уже есть в этом же
  файле — сеять `rating_actions` НРА сейчас же (той же выгрузкой), или
  строго по плану (сейчас только `current_ratings`, история — отдельной
  задачей вместе с парсингом новостей у всех 4 агентств разом)?** Данные
  просто лежат в уже скачанном файле — досеять почти бесплатно, но это
  расширение первоначального периметра задачи.

**НКР (ratings.ru) — тоже прямая Excel-ссылка, ИНН текстом, снимок
"сейчас" (без истории):**
- "Выгрузить в Excel" на `/ratings/issuers/` — статическая ссылка
  `/issuers.php`, отдаёт `.xlsx` напрямую, без параметров/токенов.
- Колонки (на английском): `ID, Issuer Name, Date, Rating, Outlook, SCA,
  Sector, TIN, OGRN, ESG-Rating, Press release`.
- 259 строк — **одна строка на эмитента** (не история, `Date` — дата
  последнего рейтингового действия). Как раз то, что нужно для первого
  шага без доработок.
- `TIN` хранится КАК ТЕКСТ (в отличие от НРА) — ведущие нули не
  теряются: у 2 региональных ИНН из 259 нули на месте. 2 других значения
  — буквально "—" (эмитент без ИНН, скорее всего иностранный) —
  корректно уходят в "не сопоставлено", не в ошибку.
- `Outlook` — на русском, но словарь шире 4 значений схемы: помимо
  `стабильный`/`позитивный`/`негативный` встречаются `рейтинг на
  пересмотре с возможностью понижения`, `рейтинг на пересмотре —
  неопределённый прогноз`, `прогноз отозван`, `—`, `неопределённый`.
  Всё, что не сводится однозначно к одному из 4 значений схемы —
  `NULL`, не приблизительная догадка направления (`RatingsNormalizer::mapOutlook()`).

## Реализовано

- **`src/Ratings/XlsxReader.php`** — минимальный читатель `.xlsx` (ZIP +
  XML) без внешних зависимостей: первый лист, строки как assoc-массивы
  "имя колонки => значение" (имя берётся из первой строки листа).
- **`src/Ratings/IssuerMatcher.php`** — сопоставление по ИНН
  (`findIssuerIdByInn`), с нормализацией потерянного ведущего нуля.
  **Нечёткое сопоставление по названию не реализовано — оказалось не
  нужно**: все 3 доступных агентства дают ИНН тем или иным путём.
  Если такое агентство всё же найдётся, это будет осознанная отдельная
  задача, а не добавленный "про запас" код.
- **`src/Ratings/RatingsNormalizer.php`** — общие для обоих Excel-агентств
  преобразования: `mapOutlook()` (русский текст → ENUM схемы, честный
  `NULL` для не влезающих в 4 значения), `parseDate()` (`ДД.ММ.ГГГГ` → `DATE`).
- **`src/Ratings/RatingsHttp.php`** — HTTP-загрузчик с ретраями (тот же
  принцип, что `Iss\IssClient`), возвращает сырые байты.
- **`src/Ratings/NkrImporter.php`**, **`src/Ratings/NraImporter.php`** —
  импортёры `current_ratings` для НКР и НРА.
- **`bin/seed_ratings.php --agency=nkr|nra`** — CLI-обёртка.

**Проверено вживую, дважды: сначала против настоящих сайтов НКР и НРА
прямо из этой сессии (доступ появился после того, как пользователь
открыл домены), затем как обычный локальный regression-прогон.** В
процессе живой проверки НРА поймана и исправлена реальная логическая
ошибка: PHP приводит чисто цифровые строковые ключи массива (ИНН как
ключ) к `int`, что ломало `string`-типизацию в `importLatestRow()` —
без прогона на настоящих 935 строках эта ошибка не всплыла бы на
маленьких тестовых фикстурах, где такого совпадения условий не было.

## НРА: rating_actions досеяны (по решению пользователя)

`NraImporter` теперь одним проходом по уже скачанной выгрузке пишет и
`current_ratings`, и `rating_actions` (миграция 014 добавила
`UNIQUE KEY (issuer_id, agency, action_date)` для идемпотентного
апсерта полной истории при повторных прогонах). `rating_from`/
`outlook_from` вычисляются как значения ПРЕДЫДУЩЕГО по дате действия
того же эмитента (`NULL` у первой записи). Проверено вживую против
настоящей выгрузки: у реального эмитента (АО «Зарубежнефть») цепочка
`NULL→AAA|ru|` (стабильный), затем `AAA|ru|→AAA|ru|` (стабильный→стабильный)
дважды подряд — расчёт корректен.

## Эксперт РА — импортёр реализован и прогнан вживую целиком

## АКРА — закрыта: сработала защита от ботов после пары запросов

С этой машины `www.acra-ratings.ru` изначально была недоступна (битый
TLS-сертификат при переподписи прокси сессии — инфраструктурная
проблема не на нашей стороне). Пользователь открыл доступ к домену и
попробовал достучаться со своего сервера напрямую (`bin/debug_rating_page.php`,
без прокси) — и вот что выяснилось:

- Сайт — 1С-Битрикс (`/bitrix/js/...`, `/bitrix/cache/js/s1/acra/...`),
  не SPA-фреймворк. Список эмитентов на `/ratings/issuers/` не
  сервер-рендерится в HTML (0 таблиц, только меню/форма фильтра —
  типичный битриксовый "умный фильтр", подгружающий результаты через
  AJAX к тому же компоненту).
- На странице подключён `captcha-api.yandex.ru/captcha.js` (Yandex
  SmartCaptcha) — при первой проверке капча не встретилась в тексте
  страницы (0 совпадений на "captcha"), то есть не обязательно стоит на
  пути к самому списку.
- **Второй-третий запрос подряд с того же сервера получил `403 Forbidden`
  с `Transaction ID` — классическая блок-страница WAF** (анти-бот
  защита сработала на повторных запросах, не на первом).

**Решение — останавливаемся здесь, так же честно, как с ФНС.** Не
пытаемся понять, как обойти WAF/капчу (менять UA, добавлять задержки
специально под их защиту, разбираться в Transaction ID и т.п.) —
это ровно то же самое ограничение, что действовало для
service.nalog.ru с самого начала проекта, и оно не зависит от того,
какое агентство/сервис на другом конце. **АКРА остаётся нереализованной
на неопределённый срок** — 3 агентства из 4 (Эксперт РА, НРА, НКР) уже
дают реальные данные (309 из 501 эмитента с хотя бы одним рейтингом на
момент первого боевого прогона), это рабочий результат уже сейчас.

Если пользователь захочет вернуться к АКРА в будущем — единственный
честный путь (без обхода защиты) это либо у них появится официальный
API/выгрузка без такой защиты, либо забирать данные вручную (глазами,
не автоматизированным опросом) в объёме, который капча/WAF сочтут
нормальным поведением человека, а не бота.

## АКРА — переоткрыта: `current_ratings` из файла, который готовит сам пользователь

Именно так и произошло: пользователь предоставил `acra_issuers_smoketest.json`
(3 строки, полученные не автоматизированным опросом их сайта, а каким-то
своим способом — сам факт, что данные уже лежат в файле, для нас
эквивалентен Excel-выгрузке НРА/НКР, просто в формате JSON). Реализован
`AcraImporter` — **он никогда сам не обращается к acra-ratings.ru**, только
читает уже готовый локальный файл. Это не нарушает решение выше — граница
"не обходим защиту от ботов" была про то, что НАШ КОД не должен пытаться
достучаться до защищённого сайта автоматизированно; она не запрещает
пользователю самому получить данные легальным для него способом и отдать
их нам для импорта, как с любым другим источником.

Формат файла, подтверждённый на реальном примере:
```json
[{"id":46608,"company":"ПАО \"БАНК ПСБ\"","inn":"7744000912",
  "rating":"AAA(RU)","forecast":"Стабильный","date":"28 авг 2026",
  "url":"https://www.acra-ratings.ru/ratings/issuers/24/"}]
```
- `inn` может быть `null` (пример: "город Томск" — у муниципалитета нет
  ИНН юрлица) — такие строки честно пропускаются, без сопоставления по
  названию.
- `date` — формат "28 авг 2026" (день, сокращённое русское название
  месяца, год), не `ДД.ММ.ГГГГ` как у НРА/НКР — отдельный метод
  `RatingsNormalizer::parseRussianMonthDate()`.
- `forecast` — обнаружилось новое слово в словаре прогнозов: АКРА пишет
  "Развивающийся" там, где остальные агентства говорят "неопределённый"
  (тот же смысл — S&P-style "developing", другое слово). Добавлено в
  `RatingsNormalizer::mapOutlook()`.
- `rating` — формат "AAA(RU)"/"BBB+(RU)", отличается от нотации других
  агентств ("ruAA", "AA.ru"), но укладывается в `VARCHAR(20)` без
  изменений схемы.

Запуск: `php bin/seed_ratings.php --agency=acra --file=/path/to/acra_issuers.json`
(файл обязателен — без него команда завершится ошибкой с объяснением, а
не попытается сама что-то скачать).

Проверено локально на реальном файле из 3 строк: 2 сопоставились
корректно (ИНН → issuers, рейтинг/прогноз/дата распознаны верно), 1
(без ИНН) корректно пропущена.

## Скрипт пользователя для АКРА — отклонён (антифлуд/WAF-обход)

Пользователь прислал свой `bin/parse_acra_issuers.php` — рабочий полный
краулер `www.acra-ratings.ru` (внутренний JSON-эндпоинт
`/local/ajax/get_rate_person.php` + карточка на ИНН) со склеенным
CA-бандлом (докомплектован недостающим промежуточным сертификатом
GlobalSign — это само по себе нормально, не отключение проверки).
Отказался его дорабатывать (ни сохранение в БД, ничего): в его же
докблоке честно описан антифлуд сайта (503 "too many requests",
блокировка всего сайта на несколько минут), и вокруг этого построены
exponential backoff, джиттер к паузам (специально против регулярности
таймингов) и "cooldown" с продолжением после блокировки — по сути та же
категория, что и WAF-стена 403 у Эксперт РА чуть раньше в этом же
файле, просто другой код ответа и другой механизм защиты. Граница
"не подстраиваем технику под защиту от ботов" — общая для всех
источников, не только там, где явно капча.

**Важно: формат, который этот скрипт пишет в JSON, уже полностью
совпадает с тем, что понимает `AcraImporter`** (`id/company/inn/rating/
forecast/date/url`) — так что если данные для АКРА появятся каким-то
способом, не упирающимся в антифлуд (вручную, малыми порциями, через
браузер и т.п.), `bin/seed_ratings.php --agency=acra --file=...`
сработает на них без единой правки кода.

## `ManualRatingsImporter` — ручной xlsx для рейтингов, которых не нашлось на сайтах

Пользователь прислал xlsx с 16 строками — рейтинги, собранные вручную
там, где автоматические источники не сработали (не входили в
охваченные категории Эксперт РА, не совпали по каким-то причинам и
т.п.). Формат — один лист, колонки:
`ИНН | issuer_id | Полное наименование | agency | rating | outlook | last_action_date`.

Отличия от остальных источников:
- **`outlook` уже в словаре схемы** (`stable`/`positive`/`negative`/
  `developing`), не на русском — не проходит через
  `RatingsNormalizer::mapOutlook()`, а просто проверяется на
  допустимость (`ManualRatingsImporter::VALID_OUTLOOKS`); недопустимое
  значение — строка пропускается с предупреждением в лог, не тихо
  обнуляется.
- **`last_action_date` — не текст, а порядковый номер дня Excel**
  (xlsx хранит дату как число; `XlsxReader` формат ячейки не разбирает)
  — новый `RatingsNormalizer::parseExcelSerialDate()` (число дней с
  1899-12-30, стандартная поправка на "1900-как-високосный" баг Excel).
- **Файл сам называет `issuer_id`, но мы ему не доверяем вслепую.**
  `issuer_id` пересчитывается заново по ИНН через `IssuerMatcher`; если
  указанный в файле `issuer_id` расходится с тем, что реально даёт
  ИНН, — строка пропускается целиком и расхождение явно называется в
  отчёте ("вероятная ошибка в файле"), а не тихо используется одно из
  двух значений. Два независимых источника истины, которые не сходятся,
  — сигнал остановиться, не повод довериться одному наугад.

**По пути найден и исправлен реальный баг в `XlsxReader`:** он разбирал
только строки через `sharedStrings.xml` (`t="s"`), а `openpyxl` (и,
вероятно, другие генераторы xlsx, не только Excel/LibreOffice) пишет
строки инлайново (`<c t="inlineStr"><is><t>...</t></is></c>`, без
`sharedStrings.xml` вообще) — такие ячейки читались как пустая строка
молча. Это не только тестовый артефакт: реальный файл пользователя тоже
может быть переоткрыт/пересохранён каким-то инструментом, который пишет
именно так. Теперь оба варианта разбираются одинаково корректно.

Запуск: `php bin/seed_ratings.php --agency=manual --file=/path/to/ratings.xlsx`

Проверено локально: на реальном файле пользователя (16 строк) —
корректно записана строка с совпавшим `issuer_id`, корректно поймано
намеренно подставленное расхождение `issuer_id`, корректно отмечены как
несопоставленные ИНН, которых нет в тестовой базе. Отдельно, на
синтетическом xlsx — корректно отклонены неизвестное агентство и
недопустимый `outlook`, и корректно принят пустой `outlook` (→ `NULL`).
Полный регрессионный набор (securities/bondization, fns_blocks, offers,
nra, nkr, acra) — без изменений.

## Парсинг новостей — НКР и Эксперт РА реализованы (`rating_actions`)

По решению пользователя переходим к парсингу новостей всех агентств:
АКРА через WAF не пробуем (см. ниже), НРА — через email-подписку
(вне этого кода), НКР и Эксперт РА — скриптом. Оба реализованы и
проверены вживую.

**НКР** (`ratings.ru/ratings/press-releases/`) — та же таблица на 1040+
строк, что уже использовалась для разведки. ИНН в заголовке НЕ даётся
(только название, часто в падеже — "Трансстройбанка", "Селигдара" —
ненадёжно для сопоставления), зато у каждого пресс-релиза есть отдельная
страница с чистым полем "Идентификационный номер налогоплательщика
(ИНН) рейтингуемого лица" — по одному запросу на кандидата. Заголовки
очень регулярные: "НКР повысило кредитный рейтинг X с A до B, прогноз
изменён на C" — `rating_from`/`rating_to`/`outlook_to` почти всегда
разбираются прямо из текста. `NkrNewsImporter`.

**Эксперт РА** (`raexpert.ru/news/`, вкладка "Пресс-релизы") — лента
подгружается через AJAX (`/articles/news/ajax-get-news/?page=N&CSRFToken=`,
инфинити-скролл на сайте). ИНН тут не даётся вообще ни на списке, ни на
странице новости — сопоставление только по названию в кавычках из
заголовка (см. ниже, "модель сопоставления"). `ExpertRaNewsImporter` +
`ExpertRaClient::fetchNewsItems()`.

**Общее:**
- `RatingActionsWriter` — вынесенный общий апсерт в `rating_actions`
  (тот же, что уже использовал `NraImporter` для истории НРА).
- Инкрементальность: перед разбором запрашивается `MAX(action_date)`
  уже записанных действий агентства, лента/список (оба отсортированы по
  убыванию даты) разбираются только до этой границы — на повторных
  прогонах не перезапрашиваем то, что уже видели. **Ограничение,
  которое стоит знать:** граница основана на том, что реально ЗАПИСАНО,
  а не просмотрено — новость, пропущенная из-за несопоставленного на тот
  момент эмитента, сама не пересматривается позже, даже если эмитента
  потом добавили в `issuers`. Флаг `--full` игнорирует границу — стоит
  гонять периодически, не каждый день.
- Классификация "это кредитное рейтинговое действие или нет" — по
  глаголу в начале ("НКР повысило/присвоило/...", "«Эксперт РА»
  повысил/присвоил/...") плюс наличие "кредитный рейтинг" в тексте —
  так честно отсеиваются ESG-мнения, верификации облигаций и подобное
  (у Эксперт РА реально встретилось: "«Эксперт РА» выразил независимое
  мнение о соответствии облигаций... принципам социальных инструментов
  финансирования" — не рейтинговое действие, корректно пропущено).
- Отзыв рейтинга (НКР "отозвало", Эксперт РА "отозвал") — `rating_to`
  = литеральное `'отозван'`, тот же приём, что уже был у Эксперт РА в
  `current_ratings.rating` — честный статус, не выдуманный грейд.

### Модель сопоставления по названию (`IssuerMatcher::findIssuerIdByName`)

По прямому запросу пользователя — понадобилось там, где ИНН взять
неоткуда (Эксперт РА). **Точное** совпадение после нормализации (без
кавычек/организационно-правовой формы/регистра) — не расстояние
Левенштейна и не подстрока. Индекс "нормализованное имя → id" строится
один раз на прогон из `issuers.full_name`/`short_name` (обе стороны).
Неоднозначность (два разных эмитента дали одно нормализованное имя) —
намеренно не сопоставляем ни с одним, это тоже "не нашли".

Из заголовка пробуются ВСЕ названия в кавычках по порядку появления,
первое найденное в `issuers` побеждает — заголовок вида "рейтинг
облигациям серии X, планируемым к выпуску АО «Y»" может содержать
несколько кандидатов, не только имя компании.

**Кейс "ООО-пустышка для привлечения долга"** (см. запрос
пользователя) — подтвердился на практике прямо в заголовках НКР:
"НКР подтвердило кредитные рейтинги ООО «ПК Борец» и облигаций ООО
«Борец Капитал» на уровне A-.ru" — операционная компания и её SPV
упомянуты в одном действии. Для первого прохода берётся ПЕРВОЕ
(обычно главное, операционное) лицо; отдельная обработка второго —
не в этом заходе.

### Реальные баги, пойманные только на живых данных

- **XPath `contains(@class, "b-articles-list-item")` ловил и сам
  контейнер новости, И его дочерний `b-articles-list-item__info`**
  (подстрока, не точное совпадение класса) — каждая новость
  попадала в список дважды. Исправлено на явную проверку границ
  токена класса (`concat(' ', @class, ' ')` с пробелами).
- **Эксперт РА нередко называет старый И новый прогноз в одном
  предложении** — "прогноз по рейтингу изменён с НЕГАТИВНОГО на
  РАЗВИВАЮЩИЙСЯ" — общий разбор по корню слова (`mapOutlookFromProse`)
  находил "негативн" раньше "развивающ" просто по порядку проверки,
  хотя это старое значение. Добавлен прицельный паттерн "прогноз ...
  на <слово>" (после "на" в такой конструкции — всегда новое значение),
  общий разбор — только как запасной вариант.
- `fetchNewsItems()` изначально скачивал ВСЕ страницы ленты, и только
  ПОТОМ вызывающий код применял инкрементальную границу — это сводило
  на нет весь смысл инкрементальности (каждый прогон качал бы всю
  историю заново). Добавлен `$stopBeforeDate` — обход прекращается
  сразу, как только на очередной странице не осталось новостей нужной
  даты или новее.

Все три пойманы и исправлены именно на живом прогоне против настоящих
сайтов, не на тестовых фикстурах — маленькие синтетические примеры не
воспроизводили ни один из них (дублирование зависит от реальной
вложенности классов на сайте, конфликт прогнозов — от реальной
формулировки предложения, инкрементальность — от реального объёма
истории).

## НКР (новости) — outlook_from, составные действия, защита от sf (сентябрь 2026)

По решению пользователя, четыре доработки `NkrNewsImporter` разом:

**1. `outlook_from` больше не всегда `NULL`.** Источники по убыванию
надёжности: (а) `outlook_to` предыдущей по дате записи `rating_actions`
этого же `issuer_id`+`agency` — самый надёжный; (б)
`current_ratings.outlook`, но **только если** сам снимок кэша старше
записываемого действия (`last_action_date < action_date`) — без этого
условия возможна тихая ошибка: по cron-расписанию `current_ratings`
для НКР досеивается РАНЬШЕ новостного парсинга в тот же день, и кэш
может уже отражать САМО это действие (тогда `outlook_from` оказался бы
равен новому прогнозу, а не старому); (в) честный `NULL`, если ни
то ни другое не нашлось.

**2. Составные действия** (операционная компания-поручитель + её
SPV/облигационная "прокладка" в одном заголовке, например "НКР
подтвердило кредитные рейтинги ООО «ПК Борец» и облигаций ООО «Борец
Капитал» на уровне A-.ru") — теперь пишутся ПО ОБОИМ юрлицам, если оба
есть в `issuers`. Проверено вживую на реальной странице пресс-релиза:
блок "Регуляторное раскрытие" даёт ИНН только первого (главного) лица —
второе сопоставляется запасным путём, точным совпадением по имени
(`IssuerMatcher::findIssuerIdByName`, тот же механизм, что и у Эксперт
РА). Правило: пишем строку на каждый различный сопоставившийся
`issuer_id` — оба есть → 2 строки с одинаковым `rating_to`/`outlook_to`
(агентство само даёт один уровень на оба лица); только одно (любое) →
1 строка; ни одного → в "не сопоставлено". Реализация вынесена в
`resolveIssuerIds()`.

**3. Защита от нестандартных шкал (`sf` и подобное)** — такие действия
пропускаются целиком, не пишутся с обычным грейдом национальной шкалы.
Проверено вживую (10+ страниц истории, полнотекстовый поиск по сайту,
страница методологий/шкал) — НКР, похоже, вообще не рейтингует
структурированные инструменты, барьер оставлен на будущее.

**4. Разбор текста заголовка вынесен в `NkrTitleParser`** — чистый,
без БД/сети, статические методы. Причина: тестируемость (юнит-тесты на
голых строках) и переиспользование — `bin/simulate_nkr_news.php`
(новый, см. ниже) разбирает заголовки ТЕМ ЖЕ кодом, что и продакшен-
импортёр, а не отдельной копией логики.

### Два реальных бага, пойманных только на живом прогоне

`bin/simulate_nkr_news.php` (см. ниже) прогнан против настоящего
`ratings.ru` — нашёл 2 расхождения с тем, что предполагалось "на
бумаге":

- **Дефолтный грейд `D` (и, видимо, `SD`) НКР пишет БЕЗ суффикса
  `.ru`** — реальный заголовок: "...снизило кредитный рейтинг ООО
  «Бизнес-Лэнд» с CC.ru **до D**". Регэксп грейдов требовал `.ru` у
  обеих частей "с X до Y" — второй грейд не находился вообще, и
  `rating_to` ошибочно оставался равен СТАРОМУ значению (`CC.ru`).
  Исправлено: `\bD\b`/`\bSD\b` добавлены в список распознаваемых
  грейдов отдельной веткой.
- **Не всё в «ёлочках» у НКР — название юрлица.** Реальный заголовок:
  "...ООО «ЛКХ» с B.ru до CC.ru, прогноз — **«рейтинг на пересмотре с
  возможностью понижения»**" — вторая пара кавычек цитирует статус
  прогноза, не компанию. Без фильтра это ложно триггерило "составное
  действие". Исправлено двумя эвристиками в
  `NkrTitleParser::extractQuotedNames()`: название юрлица всегда
  начинается с заглавной буквы (цитата статуса — со строчной), и
  дополнительно отсекаются кандидаты со словами
  "рейтинг"/"прогноз"/"пересмотр".

Также вживую подтверждено (не баг, а сознательно корректное поведение):
заголовки вида "НКР изменило прогноз по кредитному рейтингу ООО «Х» на
«рейтинг на пересмотре...»" (глагол "изменило" не в списке `VERBS`, да
и грейда в тексте всё равно нет) корректно пропускаются целиком — это
объявление статуса "на пересмотре", не сводится ни к ENUM `outlook`,
ни к обычному грейду `rating_to`, честно вне периметра схемы.

### `bin/simulate_nkr_news.php` — сухой прогон без БД

Новый инструмент: разбирает реальную ленту `ratings.ru` (список +
детальные страницы ради ИНН) через `NkrTitleParser`, печатает, что
получилось бы (`rating_from`/`rating_to`/`outlook_to`, первичный ИНН,
названия-кандидаты, отметка составных действий), **ничего не пишет в
БД** — специально для проверки логики без доступа к реальной `issuers`.
`--limit=N` (по умолчанию 20) ограничивает число обрабатываемых строк
списка (самые свежие) — гонять всю историю (1000+ строк, по 1 доп.
запросу на страницу за штуку) незачем для проверки логики.

### `source_title` — сырой заголовок пресс-релиза в БД (миграция 015)

По прямому запросу пользователя, после того как в отчёте по живому
прогону (см. ниже) он увидел колонку с полным текстом заголовка и решил,
что её стоит хранить не только в отчёте, а прямо в `rating_actions`.
Новая колонка `source_title VARCHAR(500) NULL` — заголовок пресс-релиза
ДОСЛОВНО, без разбора, рядом с `source_url`. Не участвует в вычислении
`rating_from`/`rating_to`/`outlook_from`/`outlook_to` — отдельное поле
для provenance/аудита: если разбор когда-нибудь ошибётся (как уже дважды
случалось вживую, см. выше), можно свериться с исходным текстом прямо в
БД. Заполняется всеми тремя источниками `rating_actions`:
`RatingActionsWriter::upsert()` (используется `NkrNewsImporter` и
`ExpertRaNewsImporter`) получил новый опциональный параметр
`$sourceTitle`; `NraImporter` (пишет напрямую, без общего writer'а)
берёт значение из колонки Excel-выгрузки "Название пресс-релиза".

Живой прогон (2 сентября 2026, `--limit=70`, после обеих правок выше):
68 из 70 строк успешно разобраны (2 — корректно пропущенные "на
пересмотре"-объявления без грейда, см. выше), **3 составных действия**
найдены и правильно распознаны (Борец/Борец Капитал, ФИНБРИДЖ/ПКО ЮСВ,

## НКР (новости) — переход на автоматическое расписание каждые 30 минут (сентябрь 2026)

По прямому запросу пользователя: парсинг пресс-релизов НКР должен
запускаться каждые 30 минут и забирать только новые действия, не
перезаписывая и не дублируя уже записанные строки. Старая инкрементальность
(`MAX(action_date)` уже записанных действий) для этого не годилась — см.
причину в докблоке `NkrNewsImporter`. Три связанных решения пользователя:

**1. Дедуп — по URL пресс-релиза, отдельная таблица-журнал.**
Пользователь сам предложил URL как ключ; уточнение — `rating_actions`
физически не может быть этим журналом (не получает строку для
несопоставленных релизов). Новая таблица `rating_news_log` (миграция
`database/016_rating_news_log.sql`, `UNIQUE (agency, source_url)`):
`status='matched'` — обработан окончательно, не трогаем больше никогда;
любой другой статус (`skipped_unmatched`/`skipped_not_rating`/
`skipped_no_grade`/`skipped_non_standard`) — пробуем заново на каждом
прогоне. Это заодно автоматически чинит старую известную проблему
("эмитента добавили в issuers позже — пропущенное действие само не
подхватывалось, нужен был ручной `--full`") — теперь подхватится само,
на следующем же 30-минутном прогоне.

**2. Глубина окна — 2 дня для частого прогона, 14 дней для редкого "глубокого".**
Первое предложение (14/90 дней) пользователь счёл избыточным — раз
несопоставленные релизы теперь и так пересматриваются журналом на каждом
прогоне (см. п.1), большое окно не даёт дополнительной защиты, только
лишние повторные попытки на детальные страницы для давно известных
несопоставленных релизов. Согласованно: `--days=2` при каждом 30-минутном
прогоне (запас 28x над самим интервалом — переживает выходные/сбои),
`--days=14` раз в сутки — ловит эмитентов, добавленных в `issuers` больше
чем через 2 дня. `--full` (вся история с 2019 года) остаётся, но становится
редкой ручной операцией, не частью расписания.

**3. `current_ratings` обновляется теперь при каждой новой записи в `rating_actions`.**
Пользователь напомнил: `outlook_from` берём из `current_ratings`, значит
эта таблица должна оставаться актуальной к следующему действию. Смотрю на
исходный комментарий в `001_schema.sql` — так и было задумано с самого
начала ("Поддерживается через INSERT ... ON DUPLICATE KEY UPDATE при каждой
новой записи в rating_actions"), просто ни один из news-импортёров этого
не делал — отдельный `NkrImporter` (полная ежедневная выгрузка) обновлял
`current_ratings` независимо от новостного парсинга. Исправлено —
`NkrNewsImporter::syncCurrentRatings()`:
- строки в пределах одного прогона обрабатываются в ХРОНОЛОГИЧЕСКОМ
  порядке (список с сайта отдаётся по убыванию даты — кандидаты сначала
  собираются, потом проходятся в `array_reverse()`);
- апсерт в `current_ratings` — только если `action_date` этого действия не
  старше уже сохранённого `last_action_date` (защита кэша при пакетной
  обработке смеси старых пропущенных и свежих действий в одном прогоне);
- если действие не называет новый прогноз явно (`outlook_to = NULL`) —
  прежнее значение в `current_ratings.outlook` не затирается.

**Следствие — упростился и сам расчёт `outlook_from`/`rating_from`.**
Раньше `outlook_from` вычислялся трёхступенчато (сначала смотрели в
историю `rating_actions`, потом в `current_ratings` с проверкой дат).
Теперь, раз `current_ratings` на момент обработки каждой строки
гарантированно актуален (обновлён предыдущими по хронологии действиями),
достаточно прочитать его ДО записи новой строки:
- `outlook_from` = `current_ratings.outlook` на тот момент;
- `rating_from` = то, что явно дано в заголовке ("с X до Y"), а если не
  дано — тоже `current_ratings.rating` (раньше в этом случае был просто
  `NULL`; теперь честнее: рейтинг подтверждён на прежнем уровне, а не
  "неизвестен"). Действует и для отзыва — `rating_from` покажет последний
  реальный грейд перед отзывом.

**Проверено на SQLite** (реальный `NkrTitleParser`/`IssuerMatcher`, та же
логика ветвлений, что в продакшен-классе, финальный `INSERT` переписан
под SQLite-диалект): двухпроходный сценарий — первый проход с намеренно
неполной `issuers` (без "Колмар Груп"), второй проход после добавления
недостающего эмитента. Подтверждено: (а) ранее `matched` пресс-релизы во
втором проходе корректно пропускаются без повторной работы; (б) ранее
`skipped_unmatched` (Колмар Груп) корректно пробуется заново и на этот раз
успешно записывается; (в) `current_ratings` для эмитента с двумя
действиями в одном прогоне (Бизнес-Лэнд, 10.07 и 21.07) в итоге показывает
состояние ПОСЛЕДНЕГО по хронологии действия, а не перезаписывается задом
наперёд. **Не проверено на реальном MySQL** (в песочнице его нет) — как и
раньше, первый боевой прогон обязателен перед тем, как считать готовым.

**Реализовано:**
- `database/016_rating_news_log.sql` — новая таблица.
- `NkrNewsImporter` — переписан (см. докблок класса).
- `bin/seed_ratings.php --agency=nkr-news [--days=2] [--full]` — новый флаг `--days`.
- `bin/daemon_nkr_news.php` — новый: самостоятельный процесс с циклом
  (`sleep`) на случай, если на сервере пользователя нет доступа к обычному
  OS cron (пользователь не был уверен, есть ли он) — сам чередует частый
  (`--days=2`, каждые 30 минут) и глубокий (`--days=14`, раз в сутки)
  прогоны, без внешнего планировщика. Если OS cron есть — можно им и
  ограничиться (две строки в crontab, см. докблок `bin/seed_ratings.php`),
  демон тогда не нужен.

**Что осталось открытым:**
- Эксперт РА (`expert_ra-news`) на это расписание пока не переведён —
  старая логика (`MAX(action_date)` без журнала) без изменений. Таблица
  `rating_news_log` спроектирована на все агентства (колонка `agency`) —
  перевод, когда понадобится, не потребует новой миграции.
- `bin/daemon_nkr_news.php` не переживёт перезагрузку сервера сам — для
  автозапуска после перезагрузки нужен либо настоящий OS cron, либо
  супервизор процессов (systemd/supervisord/pm2), если что-то из этого уже
  используется на сервере пользователя.

## НРА (частое расписание) + статус "на пересмотре" для обоих агентств (сентябрь 2026)

Пользователь попросил аналогичный механизм автообновления для НРА,
изначально указав на `https://www.ra-national.ru/news/`.

### `/news/` оказалась не тем — реальные пресс-релизы уже приходят через Excel

Проверено вживую: `/news/` — общая PR-лента агентства (JetEngine-листинг,
пост-тип `novosti-nra`), 15 последних публикаций на момент проверки — ни
одной "НРА повысило/понизило/присвоило рейтинг ООО «Х»", только форумы и
обновления методологий. Реальные пресс-релизы по рейтинговым действиям
живут на отдельных URL `ra-national.ru/press_release/<slug>/<id>/` — и
единственный путь их получить, тот же самый Excel-файл, который уже
скачивает `NraImporter` (колонка "Ссылка на пресс релиз" — прямая ссылка
на них). Свежесть подтверждена вживую: в момент проверки самая новая
строка выгрузки была датирована ТЕКУЩИМ днём — отдельного скрейпинга
списка не нужно, всё уже приходит через существующий механизм.

### Дедуп — тот же `rating_news_log`, без полной перезаливки

Пользователя справедливо смутило, что `NraImporter` при каждом прогоне
перезаписывал ВСЮ историю (941 строка) — работало корректно, но лишняя
нагрузка на БД при частом (каждые 30 мин) прогоне. Решение — переиспользовать
`rating_news_log` (миграция 016, уже была спроектирована на все агентства):
ключ — "Ссылка на пресс релиз", `status='matched'` — не трогаем повторно,
любой другой статус — пробуем снова. Файл всё равно скачивается целиком
каждый раз (агентство не даёт иначе) — это дёшево (один HTTP-запрос,
разбор в памяти), а вот upsert'ы в `current_ratings`/`rating_actions`
теперь выполняются только для реально новых/несопоставленных ранее строк.

Общая логика чтения/обновления кэша `current_ratings` и работы с
`rating_news_log` вынесена из `NkrNewsImporter` в отдельные классы —
`CurrentRatingsSync` и `RatingNewsLog` — обоим импортёрам нужна была
ровно одна и та же логика 1:1, дублировать её не стали.

### Статус "на пересмотре" (CreditWatch) — миграция 017, найдено даже больше, чем казалось

По итогам разбора реальной Excel-выгрузки — у НРА статус наблюдения дан
**структурированной колонкой** "Под наблюдением" (`""`/`"Под наблюдением"`/
`"Снято с наблюдения"` — 602/130/209 строк на момент проверки), а не
свободным текстом, как у НКР. Колонка "Прогноз" иногда (не всегда)
дублирует статус текстом ("Стабильный - под наблюдением") — этот суффикс
отрезается (`RatingsNormalizer::stripWatchSuffix()`), а решающее слово — за
колонкой "Под наблюдением" (`combineWithWatchStatus()`).

**Важная находка при полной проверке всех 21 реальной комбинации** (Прогноз
× Под наблюдением): `under_review_negative`/`under_review_positive` у НРА
— НЕ гипотетические, как казалось по одной только колонке "Прогноз"
(там ни разу не встретилось "Негативный - под наблюдением"/"Позитивный -
под наблюдением" текстом) — они РЕАЛЬНО есть, просто видны только через
отдельную колонку "Под наблюдением" (4 и 8 строк соответственно). Разбор
только текста колонки "Прогноз" эту информацию бы потерял.

Единый словарь значений `outlook` (ENUM расширен миграцией 017, унифицирован
формат "под_review + суффикс" после того, как была замечена нестыковка
порядка слов между первой версией для НКР и первой версией для НРА):

```
positive, stable, negative, developing,               -- было
under_review, under_review_negative, under_review_positive,
under_review_stable, under_review_developing,          -- новое
review_concluded                                        -- новое
```

- `under_review*` — статус активного наблюдения (CreditWatch/Rating Watch).
- `review_concluded` — пользователь явно подтвердил: ОТДЕЛЬНОЕ значение,
  не молчаливый `NULL` — сам факт "снято этим действием" значим, даже
  когда текущий прогноз дальше не назван (НРА: "Без прогноза - снято с
  наблюдения", встретилось 36 раз в комбинации с "Под наблюдением"="Снято
  с наблюдения" + "Прогноз"="Без прогноза", не 1 раз, как казалось по
  одной лишь колонке "Прогноз").
- Правило "снято с наблюдения" + есть базовый прогноз → возвращается сам
  базовый прогноз (наблюдение закончилось, это уже обычное состояние);
  только когда базы нет (без прогноза) — `review_concluded`.

Для НКР (свободный текст, нет структурированной колонки) —
`RatingsNormalizer::extractReviewStatusFromProse()`: "на пересмотре" +
"с возможностью понижения/повышения" → `under_review_negative`/
`under_review_positive`; голое "на пересмотре" → `under_review`. Проверяется
ПЕРЕД обычным `mapOutlookFromProse()`.

### Глагол "изменило" у НКР (решение пользователя)

Добавлен в `NkrTitleParser::VERBS` — ради заголовков вида "НКР изменило
прогноз по кредитному рейтингу ООО «Х» на «рейтинг на пересмотре...»",
где грейд не называется вообще. Для этого глагола (и только для него)
отсутствие грейда в заголовке — не ошибка разбора: `rating_to` берётся из
`current_ratings.rating` (уровень не меняется, меняется только статус).
Если и в кэше пусто (первое вообще известное действие по эмитенту) —
такой issuer честно пропускается (нечего писать в `NOT NULL rating_to`).
Проверено на SQLite: реальный кейс "КЛВЗ Кристалл" (есть история в кэше)
→ пишется с `rating_to` из кэша; гипотетический "первое действие без
истории" → корректно пропускается.

## Эксперт РА — третье агентство на общую механику (сентябрь 2026)

Базовый парсинг новостей Эксперт РА (`ExpertRaNewsImporter`/
`ExpertRaClient::fetchNewsItems()`) уже существовал с более раннего
захода. Задача этой сессии — довести его до той же механики, что НКР/НРА:
`rating_news_log`, `CurrentRatingsSync`, статус "на пересмотре". Живая
разведка (сентябрь 2026, `raexpert.ru/news/`) сразу дала три находки,
которых не было ни у НКР, ни у НРА.

### 1. Своя терминология статуса "под наблюдением"

Ни "на пересмотре" (НКР), ни структурированная колонка (НРА) — Эксперт РА
даёт статус свободным текстом со своими глаголами (проверено на 18
реальных примерах): "установил статус «под наблюдением»" (начат, обычно
вместе с "присвоил"), "продлил статус «под наблюдением»" (продлён —
**новый глагол** в `VERBS`, титул целиком про это без "присвоил"/
"понизил" и т.п.), "снял статус «под наблюдением»" (завершён). Направление
(positive/negative) в этой формулировке НИ РАЗУ не встретилось —
"установил"/"продлил" всегда даёт голое `under_review`. Новый метод
`RatingsNormalizer::extractWatchStatusFromExpertRaProse()`; "снял" —
то же правило, что у НРА (`combineWithWatchStatus`): база есть → база,
нет → `review_concluded`.

### 2. Нестандартные шкалы (`.sf`) — здесь это реально нужно

В отличие от НКР (ни разу не встретилось живьём) — Эксперт РА рейтингует
структурированное финансирование: 12 из 200 реальных новостей содержали
"...на уровне ruAAA.sf". Без защиты общий регэксп грейда извлёк бы просто
"ruAAA" (останавливается на точке перед "sf"), молча выдавая
structured-finance-рейтинг за обычный корпоративный. `RatingsNormalizer::
isNonStandardRating()` — тот же метод, что написан для НКР, переехал в
общий класс, когда понадобился второму агентству.

### 3. Кавычки — не только «ёлочки»

Эксперт РА непоследователен в стиле кавычек: часть названий в обычных
«ёлочках», часть — в ПРЯМЫХ кавычках (`ООО "Сибэнергомаш - БКЗ"`, `АО
"АБЗ-1"`, `ПАО "РусГидро"`). Без учёта прямых кавычек ~20% реальных
новостей (35 из 179 в тестовой выборке) уходили в "не сопоставлено", хотя
компания прямо названа в тексте. `RatingsNormalizer::extractQuotedNames()`
теперь собирает оба стиля и объединяет (общий метод — правка
автоматически подхватилась и для НКР, регрессии не дала: реальные
заголовки НКР кавычек не путают). После исправления совпадений на той же
тестовой выборке стало 158 вместо 144.

**Известное необходимое ограничение** (не решаемое кавычками вообще):
часть названий — обычно регионы/субъекты РФ ("Ульяновской области",
"Республики Башкортостан") и изредка ALL CAPS без всякой пунктуации
("АО РОСЭКСИМБАНК", "АО НОКССБАНК") — не берутся в кавычки НИКАКОГО
стиля. Для BondKeeper (фокус на корпоративных облигациях, не суверенном/
субфедеральном долге) — по всей видимости, не критично, но не чинится
этим методом в принципе.

**Также подтверждено вживую: составных действий (компания-поручитель +
её SPV в одном заголовке, как у НКР) у Эксперт РА в реальных данных НЕТ**
(проверено на 200 новостях — то, что похоже на составное, оказывалось
либо самим "«Эксперт РА»" в кавычках, либо ложным срабатыванием на
"под наблюдением"/классы траншей структурированного финансирования,
все реальные случаи закрываются фильтрами выше). `ExpertRaNewsImporter`
сознательно НЕ получил multi-issuer логику НКР — она не нужна для
реально наблюдаемых данных.

### Расписание и дедуп — своё окно, без деления на частый/глубокий

`--days=14` по умолчанию (не 2, как у НКР) — у Эксперт РА нет дорогого
запроса на КАЖДУЮ строку (сопоставление по имени, не по ИНН, детальных
страниц не требуется), поэтому нет смысла экономить на узком "частом"
окне — 14 дней одинаково дёшево что каждые 30 минут, что раз в сутки.
`bin/daemon_expert_ra_news.php` — простой цикл, как у НРА, без деления на
частый/глубокий.

## Эксперт РА — поправка: ИНН всё-таки есть, просто не в ленте (сентябрь 2026)

Пользователь спросил в лоб: «Весь парсинг только по названию? ИНН нигде

  теперь ПЕРВИЧНО по ИНН (как у НКР), запасным путём — по названию в

- Счётчики `matchedByInn`/`matchedByName` в отчёте — видно, какой путь
  реально сработал.
- **Расписание — снова частый/глубокий, как у НКР** (`--days=2`/`--days=14`,

  `daemon_nkr_news.php`) — доп. запрос на детальную страницу сделал
  стоимость прогона такой же, как у НКР, узкое "частое" окно снова имеет

## АКРА, новости — почтовая рассылка вместо сайта (ШАБЛОН, сентябрь 2026)

Ранее решение по АКРА (см. разделы выше) — WAF/капча закрывает и
`/ratings/issuers/`, и `/press-releases/`, ни current_ratings, ни новости
через сайт не забираем. Пользователь сообщил про альтернативный источник:
АКРА сама рассылает письма "Новое рейтинговое действие" (отправитель
`АКРА <noreply@acra-ratings.ru>`) на каждый пресс-релиз. Это НЕ обход
защиты — письма приходят пользователю напрямую по подписке, наш код
никогда не обращается к acra-ratings.ru вообще, ни для чтения писем
(это отдельный протокол — IMAP к почтовому ящику), ни тем более для
перехода по ссылкам внутри них (см. ниже).

**Формат письма** — подтверждён на ~15 реальных примерах (пересланы
пользователем как текст, RU+EN версия в каждом письме, разбирается
только русская часть): одно или несколько действий под общим заголовком
даты ("03 сентября 2026 года"), каждое — одна строка
`"<Подлежащее> — <текст действия>"` с длинным тире. Полный разбор находок
(глаголы, ISIN, опечатка "cтабильный", "также"-хвосты, международная
шкала без "(RU)") — в докблоке `AcraEmailParser`, не дублирую здесь.

**Находка: ссылка в письме — расшифровывается, не открывается.** Реальная
ссылка из письма:
```
https://uni.acra-ratings.ru/ru/mail_link_tracker?hash=...&url=aHR0cHM6Ly93d3cuYWNyYS1yYXRpbmdzLnJ1L3ByZXNzLXJlbGVhc2VzLzcyMzgv&uid=...&ucs=...
```
`url=` — base64 настоящего адреса пресс-релиза:
`https://www.acra-ratings.ru/press-releases/7238/` (расшифровано и
проверено вживую на этой конкретной ссылке). `uid=` — личный ID подписки
пользователя на рассылку АКРА, поэтому в БД сохраняем не сырую ссылку из
письма, а РАСКОДИРОВАННЫЙ канонический адрес (`AcraMailImporter::
resolveCanonicalUrl()`) — и как дедуп-ключ (`rating_news_log.source_url`),
и в `rating_actions.source_url`. Ссылка НИКОГДА не запрашивается по сети.

**ISIN как дополнительный путь сопоставления.** Часть писем — про рейтинг
КОНКРЕТНОГО выпуска облигаций ("Облигации ООО «Х» серии ... (ISIN)") — с
ISIN прямо в тексте. Добавлен `IssuerMatcher::findIssuerIdByIsin()`
(`SELECT issuer_id FROM securities WHERE isin = ...`) — потенциально
закрывает категорию "регион/субъект РФ без ИНН и без кавычек", которая у
Эксперт РА была принципиально нерешаемой (у муниципалитета нет ИНН
юрлица, но у его облигационного выпуска есть свой ISIN). ИНН в письмах
АКРА не встречается вообще — основной путь сопоставления, как и раньше,
по точному имени в кавычках (`RatingsNormalizer::extractQuotedNames()`);
ISIN — бонусный запасной путь, не основной механизм (сам пользователь
обоснованно ожидал, что он покроет меньшинство писем).

**Реализовано как ШАБЛОН, не как готовое решение** — по прямой просьбе
пользователя ("напиши шаблон... разработчик сам разберётся"):
- `AcraEmailParser` — чистый разбор текста, БЕЗ каких-либо внешних
  зависимостей (IMAP/БД) — единственная часть, которую удалось проверить
  тем же способом, что и у остальных агентств: прогнан на всех 22
  реальных строках действий из присланных писем, все 22 распознаны
  верно (грейд, прогноз с учётом опечатки, ISIN, статус "под
  наблюдением", "eXXX(RU)"-ожидаемые рейтинги, международная шкала без
  "(RU)") — см. `test_acra_parser.php` в истории сессии, не вошёл в
  поставку (черновой скрипт).
- `AcraMailImporter` — оркестрация (IMAP-подключение, поиск новых писем,
  разбор MIME на HTML-часть, дедуп через `RatingNewsLog`, запись через
  `RatingActionsWriter`/`CurrentRatingsSync` — переиспользует ту же общую
  механику, что и все остальные агентства). ЭТА часть НЕ проверена
  вживую — в песочнице разработки нет ни `ext-imap`, ни доступа к
  реальному почтовому серверу. Самое слабое место —
  `extractLinkedActionLines()`/`extractLinkMap()`: предположение о том,
  как именно ссылка стоит в HTML-разметке письма (на всём тексте
  подлежащего целиком или частично), никем не подтверждено — если карта
  ссылок не совпадёт со строками действий, код НЕ упадёт (дедуп-ключ
  просто откатится на Message-ID письма), но разработчику стоит
  перепроверить на 2-3 реальных письмах и поправить эту функцию под
  фактическую разметку.
- Расписание — как у НРА (простой цикл каждые 30 минут, БЕЗ деления на
  частый/глубокий): в письме уже есть вся нужная информация, доп.
  HTTP-запроса на строку, как у НКР/Эксперт РА, здесь нет — экономить
  нечего. `bin/daemon_acra_news.php` по образцу `daemon_nra.php`.
- Учётные данные ящика — `config/acra_mailbox.php` (шаблон —
  `acra_mailbox.example.php`, реальный файл в `.gitignore`), по тому же
  принципу, что `config/proxies.php` у Эксперт РА: секреты отдельно от
  кода. Домен ящика на момент подготовки — `kvint-invest.com`, MX
  указывает на `mail.kvint-invest.com` (самостоятельный почтовый сервер,
  не Microsoft 365/Google Workspace — судя по MX, обычный IMAP+пароль
  должен работать без OAuth, но это ПРЕДПОЛОЖЕНИЕ по MX-записи, не
  проверено фактическим подключением).
- Рекомендация пользователю (не сделано автоматически — нет доступа к
  его почте): завести в ящике отдельную IMAP-папку для писем АКРА
  (правило "от noreply@acra-ratings.ru — переместить в папку ACRA") —
  так `AcraMailImporter` читает только нужные письма, не весь общий
  почтовый поток; путь к папке — `AcraMailboxConfig::$folder`.

**Что осталось открытым:**
1. IMAP-часть (`AcraMailImporter`) не проверена ни разу вживую — первый
   реальный прогон на стороне разработчика/пользователя обязателен,
   особенно разметка ссылок (см. выше).
2. Глаголы "повышен"/"отозван"/"снят статус «под наблюдением»" (снятие,
   не установление) добавлены по аналогии с остальными тремя
   агентствами — ни разу не встретились в присланных примерах, требуют
   подтверждения на реальных данных.
3. "также пересмотрен рейтинг выпусков..." (единственный пример — ГПБ
   Финанс) — направление/новое значение не даётся, намеренно не
   разбирается на структурированные поля, только хранится как есть в
   `source_title`.
4. current_ratings для АКРА по-прежнему опирается на ручной JSON-файл
   (`AcraImporter`/`--agency=acra`) — эта работа про `rating_actions`
   (историю действий), не про полный охват текущих рейтингов.

## Сведение двух параллельных веток разработки (сентябрь 2026)

Параллельно с работой, описанной в разделах выше по свежей метке
времени ("НКР (новости) — переход на автоматическое расписание...",
"НРА (частое расписание)...", "Эксперт РА — третье агентство...",
"АКРА, новости — почтовая рассылка...") велась ДРУГАЯ, независимая
реализация той же задачи ("скользящее окно новостей") в основной
рабочей сессии этого репозитория — доведённая до боевого использования
(миграция `015_rating_actions_review_queue.sql`: nullable `issuer_id`/
`rating_to` прямо в `rating_actions`, ключ апсерта `source_url`,
`has_unresolved_fields`/`unresolved_fields`), уже применённая на
проде и уже реально прогнанная (`nkr-news`/`expert_ra-news`) к моменту,
когда пользователь передал 4 пакета выше для сравнения.

**Пользователь явно решил** — архитектура из этих 4 пакетов принимается
как основная (проверена вживую на всех 4 агентствах, а не только двух;
решает несколько реальных багов, не пойманных в первой ветке — порядок
обработки строк, "не затирать outlook кэша нулём", D/SD-грейды без
`.ru`, `.sf`-шкалы, прямые кавычки у Эксперт РА, составные действия
НКР с несколькими issuer_id на одну новость). Реализована как замена,
не как надстройка:

- **Миграция `016_rating_actions_source_title.sql`** (не
  `015_rating_actions_source_title.sql`, как в пакетах выше — номер
  15 уже занят в основной ветке) — ОТКАТЫВАЕТ миграцию 015 к состоянию
  миграции 014 (`issuer_id`/`rating_to` снова `NOT NULL`, ключ апсерта
  снова `UNIQUE(issuer_id, agency, action_date)`, `has_unresolved_fields`/
  `unresolved_fields` удалены) и добавляет `source_title`. Поскольку
  на проде к этому моменту уже реально существовали строки с
  `issuer_id`/`rating_to IS NULL` (записанные первой веткой), миграция
  сама удаляет такие строки и разрешает возможные дубли по
  `(issuer_id, agency, action_date)`, возникшие, пока действовал ключ
  по `source_url` — см. докблок самой миграции, там разбор подробный.
  Ничего не теряется: такие пресс-релизы просто не были ещё занесены в
  `rating_news_log` (той таблицы ещё не было) — миграция 017 создаёт
  таблицу, а первый же следующий прогон `nkr-news`/`expert_ra-news`
  видит эти пресс-релизы заново в пределах своего окна `--days` и
  либо распознаёт правильно, либо честно логирует статус попытки.
- **Миграции `017_rating_news_log.sql`, `018_outlook_under_review.sql`**
  — переномерованные `016`/`017` из пакетов выше (та же нумерация была
  занята в основной ветке миграцией `016`, которой в пакетах не было
  вовсе — независимые ветки нумеровали с одной и той же точки).
  Содержимое не менялось, только имя файла/номер.
- Код (`RatingActionsWriter`, `CurrentRatingsSync` — заменил собой
  `CurrentRatingsStore` первой ветки, `RatingNewsLog`, `NkrTitleParser`,
  `RatingsNormalizer`, `IssuerMatcher::findIssuerIdByIsin()`,
  `NkrNewsImporter`, `ExpertRaNewsImporter` + `ExpertRaClient::
  fetchReleaseInn()`, `NraImporter`, `bin/seed_ratings.php`,
  `bin/daemon_nkr_news.php`/`daemon_expert_ra_news.php`/`daemon_nra.php`)
  — взят из пакетов буквально (после сверки построчным diff'ом с
  тем, что уже было в репозитории), с точечными правками только под
  переномерованные миграции.
- `NraImporter`, помимо перехода на `rating_news_log`, заодно избавился
  от синтетического `source_url` (`nra-manual:<issuer_id>:...`),
  который был добавлен в первой ветке специально под ключ апсерта
  `source_url` (часть строк истории НРА не имеет реальной ссылки на
  пресс-релиз в файле) — при возврате к составному ключу
  `(issuer_id, agency, action_date)` эта проблема просто не существует,
  `source_url` снова может быть честным `NULL`.
- **АКРА через почту (`AcraEmailParser`/`AcraMailImporter`/
  `AcraMailboxConfig`) НЕ перенесена в репозиторий в этом заходе** — по
  прямому решению пользователя корпоративный почтовый ящик под это ещё
  не заведён (создание домена `bondkeeper` и почты — отдельная будущая
  задача пользователя), а сам пакет явно маркирован как ШАБЛОН,
  IMAP-часть которого ни разу не проверялась вживую (см. раздел выше).
  Код разбора текста писем (`AcraEmailParser`) и `IssuerMatcher::
  findIssuerIdByIsin()` при этом уже перенесены (первый — самодостаточный
  чистый парсер без побочных эффектов, второй — маленький и безопасный
  метод без обращений куда-либо) — когда почта будет готова, останется
  добавить `AcraMailImporter`/`AcraMailboxConfig`/`daemon_acra_news.php`
  и разобраться с реальной разметкой писем на месте (см. открытые
  вопросы в разделе выше).
- Проверено вживую после сведения (та же основная сессия, где
  собиралась эта секция): скользящее окно (`--days=2`/`--days=30`)

# Этап 5 — уведомления о выплатах (купон, амортизация, погашение)

Стартовые шаблоны, собранные 4 октября 2026 **до** получения описания API
GetNews (НРД). Готово всё, что от API не зависит: расчёт дат, обработка
сообщения о выплате, события, тексты уведомлений, расписание. Не готово
то, что без API написать нельзя: само получение сообщений из GetNews и их
перевод в наш вид (см. раздел 8).

Оферты в этот этап не входят — к ним вернёмся отдельно.

## 1. Схема уведомлений (согласована с пользователем 04.10.2026)

| Когда | Что видит клиент | Событие | Кто создаёт |
|---|---|---|---|
| За сутки до даты выплаты **по графику**, 10:00 мск | ⏰ «Завтра выплата: купон — … ₽ на бумагу» | `R1` | `bin/payment_reminders.php` |
| Как только НРД сообщил, что получил деньги (может быть и накануне дня выплаты) | ✅ «Купон за … получен НРД: … ₽ на бумагу» | `A2` купон / `A4` амортизация / `A6` погашение | обработка сообщения НРД |
| День выплаты, 19:00 мск, сообщения о получении нет | 🟡 «Деньги от эмитента … пока не поступили» | `B2a` | `bin/payment_checks.php --at=evening` |
| Утро следующего рабочего дня, 10:00 мск, сообщения всё ещё нет | 🟡 «…до сих пор не поступили» | `B2a` | `bin/payment_checks.php --at=morning` |
| НРД сообщил: выплачено частично | 🔴 «Купон за … выплачен частично: получено X из Y» | `B1` | обработка сообщения НРД |
| НРД сообщил: не исполнено в срок | 🔴 «Купон за … не выплачен в срок. Полный дефолт наступит, если долг не будет закрыт до …» | `B2` | обработка сообщения НРД |
| Доплата после частичной выплаты | 🟡 «доплата X, всего получено Y из Z» | `B4` | обработка сообщения НРД |
| Долг закрыт после просрочки | ✅ «выплачен полностью после просрочки» | `B5` | обработка сообщения НРД |
| Вечер следующего рабочего дня, от НРД нет **вообще ничего** | клиент ничего не видит; сообщение **администратору**: возможен сбой | `B2b` | `bin/payment_checks.php --at=evening` |

«Передано депонентам» (`A3` / `A5` / `A7`) записывается в базу, но клиенту
не рассылается: деньги уже засчитаны по сообщению «получено», второе
уведомление о тех же деньгах было бы шумом.

Купон, амортизация и погашение одной бумаги на одну дату в напоминании и в
жёлтом сообщении идут **одним** уведомлением («выплата: купон — …;
амортизация — …»). Сообщения НРД по ним приходят раздельно, поэтому
«получено», «частично» и «не выплачено» — по каждой выплате отдельно.

## 2. Две даты: по графику и день исполнения

- **Дата по графику** — та, что стоит в `coupons.period_end_date`,
  `amortizations.payment_date_planned`, `redemptions.payment_date_planned`.
- **День исполнения** — та же дата, а если она выпала на выходной или
  праздник — следующий рабочий день (ст. 193 ГК РФ).

Напоминание считается от даты **по графику**: его смысл — дать клиенту
возможность продать бумагу до выплаты, поэтому о субботней выплате
напоминаем в пятницу, а не в воскресенье. В тексте при этом называется и
день, когда деньги придут на деле.

Проверки «денег пока нет» считаются от **дня исполнения**: в субботу эмитент
платить не обязан, тревога в субботу вечером была бы ложной.

Срок полного дефолта — день исполнения + 10 рабочих дней (проверено на
кейсах: СибАвтоТранс 16.04.2026 → 30.04.2026, Роял Капитал 04.05.2026 →
19.05.2026).

Рабочие дни считает `src/Payments/WorkingCalendar.php` по
`config/working_calendar.php` (2026 — постановление № 1466 от 24.09.2025,
2027 — № 1187 от 17.09.2026; в каждом году 247 рабочих дней). **Раз в год**
файл нужно пополнять следующим годом; когда до конца покрытого периода
остаётся меньше 20 дней, `payment_reminders.php` пишет об этом
администратору.

## 3. Обработка сообщения о выплате (`PaymentProcessor`)

На входе — `PaymentMessage`: сообщение источника в нашем виде.

| Поле | Что это |
|---|---|
| `sourceRef` | номер сообщения у источника — по нему отсекаются повторы |
| `isin` | бумага |
| `kind` | `coupon` / `amortization` / `redemption` |
| `paymentDate` | дата выплаты (по графику или с переносом — найдём обе) |
| `stage` | `received` — деньги получены НРД; `transferred` — переданы депонентам |
| `execution` | `full` / `partial` / `none` (не исполнено в срок) |
| `amountPerBond` | сумма на одну бумагу в этом сообщении (может отсутствовать) |
| `messageDate` | дата сообщения |
| `recordDate`, `title`, `raw` | дата фиксации, заголовок, исходное сообщение целиком |

Что делает `process()`:

1. Сохраняет исходное сообщение в `raw_messages` (source = `nsd`). Повтор с
   тем же `sourceRef` — пропуск. Сообщение, которое не удалось привязать
   (нет бумаги или выплаты в графике), остаётся со статусом `failed` и
   причиной; при повторной подаче пробуется заново.
2. Находит выплату по ISIN и **дате** (номера купона в графике нет с
   миграции 006). Сначала точная дата; если нет — единственная выплата
   этой бумаги с тем же днём исполнения в пределах ±7 дней (источник мог
   назвать понедельник, а в графике суббота).
3. Открывает или находит «историю» выплаты (`event_stories`) — одна на
   выплату: вся серия «не выплачено → транш → транш → исполнено» читается
   одной лентой.
4. Меняет строку графика (`status`, `actual_value_per_bond`,
   `full_default_date_planned`) и создаёт события:

| Было | Пришло | Стало | События |
|---|---|---|---|
| planned | получено полностью | paid, история закрыта | A2 / A4 / A6 |
| planned | передано полностью (получение не приходило) | paid | A2 / A4 / A6 и A3 / A5 / A7 |
| paid | передано | без изменений | A3 / A5 / A7 |
| planned | частично | partial, срок дефолта | B1 |
| partial / not_paid | ещё часть, долг не закрыт | partial | B4 |
| partial / not_paid | остаток или полная сумма | paid, история закрыта | B5 |
| planned | не исполнено в срок | not_paid, срок дефолта | B2 |
| partial | не исполнено в срок | partial | B2 (один раз на выплату) |
| paid | что угодно, кроме «передано» | без изменений | — |

Факт выплаты считается по сообщению **«получено НРД»**. Фактическая сумма
копится только по сообщениям о получении; «передано» те же деньги второй
раз не прибавляет. Если суммы в сообщении нет, а исполнение полное — факт
равен плану. У флоатера без плановой суммы факт берётся из сообщения.

Как именно реальные сообщения GetNews раскладываются на `stage` и
`execution` — нужно проверять на живых примерах после получения доступа
(см. раздел 9). Правила выше — ожидаемое поведение, а не подтверждённое.

## 4. Проверки по графику (`PaymentWatch`)

«Сообщения нет» = выплата в графике всё ещё в статусе `planned`: любое
обработанное сообщение НРД статус меняет.

- `remind($today)` — выплаты с датой по графику «завтра» → `R1`.
- `checkNoReceipt($today, evening)` — выплаты с днём исполнения сегодня →
  `B2a`; `morning` — с днём исполнения в предыдущий рабочий день → `B2a`
  повторно. В нерабочий день не выполняется.
- `checkSilence($today)` — выплаты с днём исполнения в предыдущий рабочий
  день, по которым до сих пор `planned` → `B2b` и сообщение администратору.

В выборку попадают бумаги в обращении (`securities.status` = `active` или
`tech_default`; погашенные, дефолтные и снятые с торгов — нет) и только
плановые погашения (`scheduled_maturity`). Повторный запуск за тот же день событий
не дублирует.

## 5. Кому уходит уведомление

Как и раньше — тем, у кого эмитент в списке отслеживания (`watchlist`), и
только по событиям, появившимся после добавления. У событий о выплатах
заполнен `events.security_id`; в запрос рассылки добавлено условие: строка
`watchlist` без `security_id` (эмитент целиком — так бот добавляет сейчас)
получает всё, строка с `security_id` — только события этой бумаги и события
уровня эмитента (рейтинг, ФНС). Сейчас это ничего не меняет; это основа
будущей настройки «уведомлять только по выбранным выпускам».

## 6. Включение

Файл `config/payments.php` (образец — `config/payments.example.php`). Пока
файла нет, всё выключено.

```php
return [
    'reminders' => false,       // true — рассылать напоминания накануне выплаты
    'checks' => 'off',          // off | admin | clients
    'getnews_polling' => false, // true — bin/poll_getnews.php реально пишет в БД
];
```

- `reminders` можно включать уже сейчас: напоминания считаются по графику и
  от НРД не зависят.
- `checks` включать **только после** того, как сообщения НРД начнут
  попадать в базу. Иначе по каждой выплате будет тревога «денег нет».
  Порядок: сначала `admin` (списки приходят только администратору — можно
  сверить с реальностью), затем `clients`.
- `getnews_polling` — ОСТОРОЖНО: включение сразу означает настоящие
  уведомления клиентам по купонам/погашениям/амортизациям (A2/A4/A6/B1/
  B2/B4/B5 уведомляют клиентов с первой миграции, отдельно для одного
  источника не выключить). Сначала несколько раз `--dry-run` (работает
  всегда, даже без этого флага) — убедиться, что разбор сообщений
  (`GetNewsMessageMapper`) даёт ожидаемый результат, и только потом
  включать.

Посмотреть, что было бы отправлено/записано, ничего не создавая:

```
php bin/payment_reminders.php --dry-run
php bin/payment_checks.php --at=evening --dry-run
php bin/payment_checks.php --at=morning --dry-run --date=2026-10-13
php bin/poll_getnews.php --dry-run
```

## 7. Расписание

Время в скриптах считается по Москве независимо от часового пояса сервера;
в крон время ставится по часам сервера. Если сервер живёт по UTC:

```
0 7  * * * php bin/payment_reminders.php            # 10:00 мск
0 7  * * * php bin/payment_checks.php --at=morning  # 10:00 мск
0 16 * * * php bin/payment_checks.php --at=evening  # 19:00 мск
```

Скрипты только создают события; рассылку делает бот
(`bin/daemon_telegram_bot.php`, проход раз в минуту). Чтобы бот знал новые
тексты, его процесс должен стартовать заново после обновления
`src/Telegram/NotificationDispatcher.php` — со старым кодом вместо текста
уйдёт заглушка «Новое событие по эмитенту».

   выплате — не подтверждено (ни одного случая в окне), см. раздел 8.
3. ~~Какая из дат корпоративного действия совпадает с датой в графике~~ —
   `action_date_plan` (пару раз — только `action_date_calc`, когда
   `action_date_plan` не заполнена; используем оба с запасным вариантом).
4. ~~Купон и амортизация одной даты — одно сообщение или два~~ — ВСЕГДА
   два разных сообщения (разные `ca_type`/`action_id`), даже если дата
   совпадает.
5. ~~Идентификатор для отсечения повторов~~ — `content_id_out`,
   подтверждён как стабильный технический id сообщения.
6. Выходит ли сообщение о неисполнении на следующий рабочий день —
   НЕ подтверждено отдельно (техдефолт обнаруживается по `state.code=T`
   в любом сообщении, не по дню выхода конкретного сообщения) — для
   `PaymentWatch::checkNoReceipt()`/`checkSilence()` (наши собственные
   расчёты по графику, не зависят от GetNews) это не критично.

Окно `--limit=1000` вернуло РОВНО 1000 записей на первом прогоне — вся

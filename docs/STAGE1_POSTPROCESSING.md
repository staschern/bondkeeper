# Пост-обработка этапа 1 — журнал решений

Первый этап (`README.md`) закрыл базовый импорт: 3061/3061 бумаг, 495
эмитентов, купоны и амортизации. Этот файл фиксирует выводы и решения по
дальнейшему разбору пропусков в `issuers`/`securities` — по мотивам
`documents/2026.08.10_BondKeeper_issuers_securities_QA.md`. Формат —
кратко, по каждому полю: что сделано / что нужно от пользователя / что
осталось открытым.

## offers — импортёр готов (`OffersImporter`, `bin/seed_offers.php`)

`OFFERDATE` подтверждён вживую (см. ниже) — `bin/debug_iss_security.php`
прогнан пользователем на 3 реальных бумагах (bondkeeper.ru, август 2026):
`RU000A0JS4Z7`, `RU000A0JSGV0` (`has_offer=1`) и `BYM000001818`
(`has_offer=0`). Результат: `OFFERDATE` в доска-специфичном эндпоинте
(`/engines/stock/markets/bonds/boards/{board}/securities/{secid}.json`,
до этой задачи в проекте нигде не запрашивался) на всех трёх бумагах
день-в-день совпал с `BUYBACKDATE`. Выборка маленькая (3 бумаги), поэтому
`OffersImporter` не полагается на то, что так будет всегда — на каждом
реальном прогоне на весь рынок он считает и логирует три группы (оба
сигнала / только `BUYBACKDATE` / только `OFFERDATE`), чтобы разошедшиеся
случаи (если они есть среди 3000+ бумаг) были видны, а не потеряны.
Строка в `offers` создаётся по **объединению**, не пересечению — если
есть хотя бы один из двух сигналов (по прямому запросу пользователя).

**Бонус-находка, не было в исходном плане:** тот же эндпоинт отдаёт
`PUTOPTIONDATE`/`CALLOPTIONDATE`. На обеих проверенных бумагах с офертой
заполнено ровно одно из двух полей — это даёт `offer_type` (put/call)
бесплатно, без похода на RusBonds (см. открытый вопрос №3 ниже — теперь
частично закрыт для тех бумаг, где сигнал однозначен). По прямому
разрешению пользователя ("Если тип оферты есть, то тогда попробуй его
сразу достать") логика реализована сразу, а не отложена: если заполнено
и `PUTOPTIONDATE`, и `CALLOPTIONDATE` (не встречалось на 3 примерах, но
не исключено на всём рынке) — либо оба пусты при наличии оферты —
`offer_type` остаётся `'unknown'`, не гадаем.

**`BUYBACKDATE` в этом эндпоинте** приходит у бумаг без оферты не как
JSON `null`, а как технический `"0000-00-00"` — та же защита
(`nullableDate()`), что уже была нужна в `SecuritiesImporter` для другого
эндпоинта. `OFFERDATE`, в отличие от него, приходит настоящим `null`.

**Запуск:** `php bin/seed_offers.php` (после `seed_market.php` — нужны
уже заполненные `securities.secid`/`moex_board`). Новая миграция не
нужна — схема (012) уже применена.

Ниже — исходная запись до подтверждения `OFFERDATE` (оставлена для
истории решения):

Первый проход — без вида оферты (put/call), только дата и признак `BUYBACKDATE`.

**Схема (миграция 012):**
- `offer_type`/`status` получили значение `'unknown'` (и default) — тот
  же принцип, что и `coupon_type` в миграции 004: честно "не знаем",
  не угадываем.
- `execution_date_planned` стал nullable — не у каждой строки в первом
  проходе будет дата (см. ниже про объединение множеств).
- `is_instruction_based` стал nullable — тоже пока не парсим.
- Новая колонка `has_buyback_date` — тот же самый флаг, что уже считает
  `securities.has_offer` (`BUYBACKDATE IS NOT NULL`), продублированный
  сюда для явной сверки с `OFFERDATE`.
- `UNIQUE KEY (security_id)` — пока одна строка на бумагу (не история
  оферт), апсерт.

**Задача от пользователя, ещё не решена — нужна проверка перед
импортом:** `has_buyback_date` и `OFFERDATE` — гипотеза, что это НЕ одно
и то же множество бумаг: может быть флаг=1 без `OFFERDATE`, и наоборот.
Собираем **объединение**, не пересечение, но сначала нужно подтвердить,
что `OFFERDATE` вообще существует в бесплатном ISS API — это поле
предположительно приходит не из уже используемого description-эндпоинта,
а из отдельного, доска-специфичного
(`/engines/stock/markets/bonds/boards/{board}/securities/{secid}.json`),
который в проекте ДО СИХ ПОР ни разу не запрашивался. Строить импортёр
на 3000+ бумаг под непроверенный эндпоинт — рискованно, поэтому сначала
проверка на нескольких примерах.

`bin/debug_iss_security.php` дополнен — теперь дополнительно бьёт по
этому эндпоинту и печатает все поля ответа с пометкой у похожих на
`OFFER`/`BUYBACK`.

**Нужно от пользователя — проверить на 2-3 бумагах, лучше по одной из
каждой группы:**
```sql
SELECT isin FROM securities WHERE has_offer = 1 LIMIT 2;
SELECT isin FROM securities WHERE has_offer = 0 AND status = 'active' LIMIT 1;
```
Затем:
```bash
php bin/debug_iss_security.php <ISIN1> <ISIN2> <ISIN3>
```
Интересует блок «проверка OFFERDATE» в выводе — есть ли там вообще поле
`OFFERDATE` (или что-то похожее), и на бумагах с `has_offer=1`/`=0`
отличается ли его наличие. По результату — либо `OFFERDATE` подтвердится
и можно писать `bin/seed_offers.php` (полноценный импортёр на весь
рынок), либо выяснится, что поля нет в бесплатном API вообще, и тогда
`offers` первое время наполняется только из `has_buyback_date`, без
`execution_date_planned`.

## Верификация переехала с issuers на fns_blocks (миграция 011)

По вашему запросу: `is_fns_blocked`/`verification`/`date_verification`/
`last_success_verification` перенесены с `issuers` на `fns_blocks`.
После миграции 010 `fns_blocks` — это уже одна строка на эмитента
(`UNIQUE KEY issuer_id`), так что состояние проверки и её результат
теперь живут в одном месте, а не в двух разных таблицах.

Раз `verification`/`date_verification` пишутся при КАЖДОЙ попытке
(включая капчу и сетевые ошибки), строка в `fns_blocks` теперь
создаётся для любого проверенного эмитента, а не только для тех, у кого
когда-либо была блокировка — иначе неудачную попытку было бы негде
отмечать. Из-за этого `block_date` стал nullable (раньше `NOT NULL`), а
`active_bank_count` по умолчанию `0`, не `1` — «проверили, блокировок
нет» тоже валидное состояние строки.

Логика снятия блокировки (`unblock_date`) сохранена без изменений по
сути: при переходе из заблокированного состояния в свободное
проставляется `CURDATE()`; если эмитент и раньше был свободен —
существующий `unblock_date` не трогается (читается ДО апдейта через
`IF(is_fns_blocked = 1, CURDATE(), unblock_date)` в `ON DUPLICATE KEY
UPDATE` — ссылка на колонку без `VALUES()` берёт значение строки на
момент ДО этого же апдейта).

Проверено локально: капча-эмитент и эмитент с сетевой ошибкой теперь
получают строку в `fns_blocks` (раньше — ни одной), с `verification =
'error'`, `is_fns_blocked = 0`, `last_success_verification = NULL`.
Трёхдневный сценарий блокировки (2 банка → 1 → 0) по-прежнему даёт ровно
одну строку с корректно обновляющимся `is_fns_blocked`/`unblock_date`.

**Действие на сервере:** миграция 011 не требует пересева данных
(только добавляет/убирает колонки) — существующие строки `fns_blocks`
получат `verification`/`is_fns_blocked` и т.п. на следующей проверке.

## fns_blocks — одна строка на эмитента, не на банк (миграция 010)

Найдено на реальных данных (ООО «Контрол Лизинг», ИНН `7805485840`):
одна и та же непрерывная блокировка периодически переиздаётся ФНС под
**новым номером решения** без факта разблокировки между ними (например
№2395737 сменился на №2454390 в одном из банков). Ключ из миграции 008
(`issuer_id, bank_bik, decision_number`) воспринимал смену номера как
«старое решение снято, новое создано» — вместо одной обновляемой строки
на банк копились дубли при каждой смене номера.

Заодно выяснилось, что дата, сумма и основание одинаковы во всех банках
одного эмитента (логично — это одна и та же налоговая задолженность,
просто счета приостановлены сразу везде, где они у компании есть) —
построчное хранение по банкам не несло дополнительного смысла, только
их количество.

**Решение:** `fns_blocks` — теперь одна строка на эмитента
(`UNIQUE KEY (issuer_id)`). Данные (дата, сумма, основание) берутся из
ПЕРВОЙ валидной строки ответа; конкретные БИК не хранятся — вместо них
`active_bank_count` (переименованный `bank_bik`) — сколько банков
одновременно заблокировано. При апдейте — просто перезапись той же
строки; при полном снятии всех блокировок — `unblock_date = CURDATE()`
на ней же (не удаляется, история одной строкой). Старые построчные
данные при миграции очищены (`DELETE FROM fns_blocks`) — это был
тестовый объём, дешевле пересобрать повторным прогоном
`check_fns_blocks.php`, чем писать конвертер для данных, часть которых
уже устарела по номерам решений.

Проверено локально: трёхдневный сценарий (2 банка → 1 банк → 0) даёт
РОВНО одну строку в `fns_blocks` на всё время, с корректно
обновляющимся `active_bank_count` и `unblock_date` только на последнем
шаге.

## Отслеживание попыток проверки ФНС (миграция 009)

**Поля ниже позже перенесены с `issuers` на `fns_blocks` — см. миграцию
011 выше.** Сама идея и мотивация не изменились, изменилось только
место хранения.

Найдено при первых боевых прогонах: неудачная попытка (капча, сетевая
ошибка) вообще не оставляла следа в БД — `issuers.fns_last_checked_at`
обновлялся только при УСПЕШНОЙ проверке. Нельзя было отличить "эмитента
ещё не проверяли" от "проверяли, но капча помешала — надо повторить".

Решение — три поля, изначально на `issuers`:
- `verification` (`success`/`error`) — чем закончилась ПОСЛЕДНЯЯ попытка;
- `date_verification` — когда была последняя попытка, вне зависимости от
  результата;
- `last_success_verification` — когда была последняя УДАЧНАЯ попытка
  (переименованный `fns_last_checked_at` — смысл тот же, имя уточнено,
  чтобы не путать с `date_verification`).

`is_fns_blocked`, содержимое `fns_blocks` и `last_success_verification`
меняются **только** при `verification = 'success'` — капча/сетевая
ошибка не трактуются как "блокировок нет", это именно "не удалось
узнать" (см. `FnsBlocksImporter::markVerificationError`).

**Почему не отдельное поле `status` на `fns_blocks`, как обсуждалось
изначально:** `issuers.is_fns_blocked` уже ровно это и есть (блокировка
есть/нет), только булево, а не `ENUM('blocked','free')` — заводить
рядом текстовый дубль было бы избыточно. А `fns_blocks` физически не
может быть "одна строка на эмитента" — у одного эмитента бывает сразу
несколько активных блокировок в разных банках одновременно (живые
примеры из реальных прогонов: ООО "СЛДК" — 6 банков, ООО "Контрол
Лизинг" — 14 банков). `fns_blocks` остаётся подробным логом по
конкретным решениям (см. миграцию 008), а верификация — на `issuers`,
где она по смыслу и должна быть.

**`blocked_amount` закрыт.** Поле `SALDOENS` — подтверждено вживую
(скриншот интерфейса сайта, колонка «Размер отрицательного сальдо ЕНС,
руб.коп», значения совпадают с БД) — это и есть искомая сумма. На самой
странице результата есть явная сноска: доступно только для кодов
основания `01`/`03` — для остальных кодов (например `06`, как у ООО
"СЛДК") поля нет вообще, и `blocked_amount` там законно остаётся `NULL`,
это не пробел. Реализовано в `FnsBlocksImporter::parseAmount()` —
значение приходит с ведущими пробелами (`"       302156193.95"`),
только тримится и проверяется на `is_numeric` перед записью.

## fns_blocks — блокировки счетов через service.nalog.ru (миграция 008)

**Схема строк по банкам ниже устарела — см. миграцию 010 выше:**
`fns_blocks` теперь одна строка на эмитента, `bank_bik`/множественные
строки на банк заменены на `active_bank_count`. Остальное про сам
источник (эндпоинт, форма запроса, капча) актуально без изменений.

Источник — официальный сервис ФНС `service.nalog.ru/bi.do`, тип запроса
«Запрос о действующих приостановлениях операций по счетам». У ФНС нет
API — это HTML-форма, под капотом реальный AJAX-эндпоинт:

```
GET  https://service.nalog.ru/bi.do          — получить свежую сессию (Set-Cookie: JSESSIONID)
POST https://service.nalog.ru/bi2-proc.json  — requestType=FINDPRS&innPRS=<ИНН>&bikPRS=<любой БИК>
                                                 (остальные поля формы — пустые строки)
```

**Подтверждено вживую (август 2026), включая голый curl без браузера —
JS-куки (Яндекс.Метрика и т.п.) не нужны, сервер отвечает нормальным
JSON:**
- `bikPRS` реально не фильтрует — ответ содержит решения по всем банкам
  эмитента независимо от переданного БИК.
- Три формы ответа, различаются набором ключей (не значением одного
  поля): (1) есть блокировки — ключ `rows` с массивом решений; (2)
  блокировок нет — ключа `rows` нет вообще (не пустой массив, а
  отсутствует); (3) нужна капча — `captchaRequired: true`, `rows` тоже
  нет. Формы (2) и (3) неразличимы без явной проверки `captchaRequired`
  в первую очередь — код обязан проверять её раньше, чем интерпретировать
  отсутствие `rows` как «блокировок нет».
- Один эмитент может иметь одновременно несколько активных блокировок в
  разных банках (живой пример — ООО «СЛДК», ИНН `1101148661`: 6 решений
  в 6 банках сразу). Естественный ключ решения — `(BIK, NOMER)`.
- Капча появляется эмпирически примерно на 3-й запрос подряд в ОДНОЙ
  HTTP-сессии (подтверждено дважды, в двух независимых сессиях: 1-й и
  2-й запрос проходят, 3-й требует капчу). Решение — не борьба с капчей,
  а обычное поведение: одна свежая сессия (`GET bi.do` заново) на КАЖДУЮ
  проверку эмитента, а не переиспользование сессии между проверками.
  **Уточнение по первому боевому прогону на сервере:** свежая сессия сама
  по себе не спасла — все 4 запроса подряд с IP сервера получили капчу
  (первый ещё в мягкой форме `HTTP 200 {captchaRequired:true}`, следующие
  три — в жёсткой, `HTTP 400 {"ERRORS":{"captcha":[...]}}}`, вторая форма
  ответа не была заложена в код изначально и до фикса считалась обычной
  ошибкой, а не капчей — см. коммит с исправлением). Похоже, ограничение
  завязано на **IP**, а не только на сессию — сервер уже успел сделать
  несколько тестовых запросов за предыдущие ~20 минут (мой curl-тест из
  переписки + этот прогон), что могло исчерпать лимит для этого IP.
  Открытый вопрос: это разовый эффект от плотного тестирования сегодня,
  или структурное ограничение, которое будет мешать и обычной,
  редкой эксплуатации. Проверяется просто — подождать (час+) и повторить
  тот же маленький список ИНН; если пройдёт чисто — дело было в
  сегодняшней плотности тестов, не в частоте реальной эксплуатации.
- Справочник кодов `KODOSNOV` (со страницы результата) — коды `01`–`06`
  (с ведущим нулём в реальном JSON, не как `1`–`6` на странице легенды —
  первая версия маппинга на это не была рассчитана и уронила
  `reason_category` в `NULL` у всех строк, поймано локальным тестом до
  деплоя). Маппинг в `reason_category`: `01`/`03` — про деньги
  (взыскание задолженности / обеспечение исполнения решения по
  налоговому правонарушению) → `tax_debt`; `02`/`04`/`05`/`06` — про
  непредставление документов/отчётности → `other`. Первое приближение,
  не финальное решение.
- **Суммы блокировки — обновление:** в первых подтверждённых ответах
  (ООО «СЛДК», код основания `06`) денежного поля не было, отсюда
  первоначальный вывод «источник сумм не даёт». Оказалось — оно есть,
  но только для кодов `01`/`03` (поле `SALDOENS`, см. отдельный раздел
  ниже про миграцию/находку с суммой) — `06` действительно без суммы,
  это структурная особенность самого кода основания, а не источника
  в целом.

**Реализация:**
- `src/Fns/NalogBiClient.php` — HTTP-клиент, свежая сессия на каждый
  вызов (создаёт и удаляет временный cookie-jar).
- `src/Fns/FnsBlocksImporter.php` — апсерт активных решений по ключу
  `(issuer_id, bank_bik, decision_number)`; решения, которые были
  активны (`unblock_date IS NULL`), но не пришли в свежем ответе,
  помечаются `unblock_date = CURDATE()` (запрос — это срез «действующих
  на сегодня», не история, отсюда и логика снятия). При
  `captchaRequired: true` — эмитент пропускается БЕЗ каких-либо
  изменений в БД, отсутствие ответа не трактуется как «блокировок нет».
- `bin/check_fns_blocks.php` — **намеренно не проверяет весь рынок по
  умолчанию** (`--limit=5` по умолчанию, либо явный список
  `--inns=ИНН1,ИНН2,...`) — пока не увидим вживую, насколько часто
  реально прилетает капча на разумном количестве эмитентов, ставить это
  в ежедневный cron по всем ~495 рано.

Проверено локально (MySQL 8, `FakeNalogBiClient`): трёхдневный сценарий
на одном эмитенте с блокировкой в 2 банках — снятие одной блокировки

## Три находки в redemptions/is_amortized (миграция 007)

По вашему прямому разбору — три отдельных, но связанных бага в
`SecuritiesImporter`/`BondizationImporter`.

**1. Дата погашения в `redemptions` считалась неизменной навсегда.**
`upsertScheduledRedemption` проверял только факт существования строки —
если она уже была, повторный `MATDATE` молча игнорировался, даже если
реально изменился (досрочное погашение, реструктуризация). Исправлено:
теперь сравнивается `redemptions.payment_date_planned` с текущим
`MATDATE`; если совпадают — строка не трогается вообще (в т.ч.
`value_per_bond`, который мог уже скорректировать `BondizationImporter`
под остаток после амортизации); если не совпадают — обновляется ТОЛЬКО
дата.

**2. `redemptions.value_per_bond` считался с двойным вычетом амортизации.**
Формула была `securities.nominal_value − SUM(вся амортизация)`, где
`nominal_value` — текущий, живой номинал (тот же `FACEVALUE`, что
синкается ежедневно и у амортизируемой бумаги УЖЕ САМ ПО СЕБЕ является
остатком после прошлых амортизаций), а `SUM` — по ВСЕЙ амортизации сразу
(bondization отдаёт график целиком, прошлые и будущие транши). Прошлая
амортизация вычиталась дважды (неявно — её уже нет в `FACEVALUE`, и явно —
она есть в сумме), плюс вычиталась вся ещё не наступившая будущая. У
бумаги с существенной историей амортизации итог легко уходил в минус.

Исправлено добавлением новой колонки `securities.initial_nominal_value`
(миграция `007`) — номинал на момент выпуска, зафиксированный один раз при
первой вставке строки (`firstPresent(['INITIALFACEVALUE', 'FACEVALUE'])`,
приоритет обратный тому, что у `nominal_value`) и НЕ входящий в
`ON DUPLICATE KEY UPDATE` — по тому же принципу, что и `created_at`.
Формула теперь: `initial_nominal_value − SUM(вся амортизация)`, вычитается
ровно один раз из неизменной базы. Заодно сумма амортизации в
`adjustScheduledRedemption` теперь считается запросом `SUM(...)` к самой
таблице `amortizations`, а не по строкам из текущего HTTP-ответа — так
пересчёт остаётся корректным, даже если конкретный сегодняшний ответ API
неполный (см. пункт 3).

**3. `is_amortized` мог тихо и навсегда стать `FALSE` из-за разового сбоя
ответа API.** Сценарий: у бумаги реально есть амортизация, но в
конкретный день bondization-эндпоинт вернул купоны полностью, а блок
`amortizations` — пустым (тот же класс сбоя, что уже случался на 435
бумагах за один день). Раньше код писал `is_amortized = 0` при любом
пустом ответе — бумага теряла флаг навсегда, а вместе с ним переставала
даже ПРОВЕРЯТЬСЯ на предмет "не пришла ли амортизация" в pending-отборе
(флаг участвует в самом условии отбора).

Исправлено двумя взаимодополняющими правками:
- `is_amortized` в `BondizationImporter` теперь монотонный — пишется
  ТОЛЬКО в `TRUE` (по факту реально вставленных строк), никогда обратно
  в `FALSE`.
- `SecuritiesImporter` независимо выставляет тот же флаг спекулятивно —
  по ключевому слову "амортизир" в `BOND_TYPE` (тот же приём, что уже
  использован для `is_structured`/`is_mortgage_backed`), ДО того, как
  `BondizationImporter` вообще увидит хоть одну строку. Пишется через
  `GREATEST(is_amortized, VALUES(is_amortized))` в `ON DUPLICATE KEY
  UPDATE` — монотонный OR, а не перезапись, поэтому текстовый сигнал
  может только включить флаг, никогда не выключить то, что уже
  подтвердил `BondizationImporter` реальными строками.
- Pending-отбор `importForAllPending()` расширен: теперь для
  `is_amortized = 1` бумаг переоткрывает их и в случае, если
  `amortizations` пуста ВООБЩЕ (не только когда есть незаполненный
  плейсхолдер) — именно это закрывает сценарий выше: текстовый сигнал
  включил флаг раньше, чем появились реальные строки, поэтому одного
  "плейсхолдер существует" было бы недостаточно.

Проверено локально (MySQL 8, `FakeIssClient`) полным двухдневным
сценарием: смена `MATDATE`, попытка перезаписать `INITIALFACEVALUE` вторым
прогоном (не сработала — колонка осталась исходной), и Ромашка-1 —
бумага с `BOND_TYPE = "Амортизируемые облигации"`, у которой на первый
день `amortizations` пришла пустой, а `is_amortized` всё равно стало
`TRUE` сразу после `seed_market.php` и осталось `TRUE` после пустого
bondization-ответа; на второй день бумага корректно переоткрылась и
получила реальную строку амортизации.

**Важный нюанс при накатке на уже заполненную БД (весь текущий рынок,
~3061 бумага, уже сидировался ДО этой миграции).** Просто исключить
`initial_nominal_value` из `ON DUPLICATE KEY UPDATE` (как задумывалось по
аналогии с `created_at`) для уже существующих строк не сработало бы —
`ON DUPLICATE KEY UPDATE` трогает только перечисленные там колонки, и
поле осталось бы `NULL` навсегда для всех, кто был в базе до миграции.
Заменил на `initial_nominal_value = COALESCE(initial_nominal_value,
VALUES(initial_nominal_value))`: для уже заполненной строки — не трогает
(старое значение побеждает); для строки, где поле ещё `NULL` (все текущие
3061 бумаги на первый постмиграционный прогон) — заполняет сегодняшним
значением из API один раз, дальше не трогает. `INITIALFACEVALUE` по
спецификации ISS — номинал на момент выпуска, сам по себе не меняется со
временем, поэтому даже "запоздалое" первое чтение для бумаги, уже давно
торгующейся и прошедшей часть амортизации, должно корректно вернуть
историческое значение, а не сегодняшний слепок.

**Действие на сервере:** накатить `007_initial_nominal_value.sql`, затем
обычный `php bin/seed_market.php` (без флагов — заполнит
`initial_nominal_value` для всех уже существующих бумаг за счёт
COALESCE-бэкфилла выше), затем `php bin/seed_bondization.php --force` —
пересчитает `redemptions.value_per_bond` уже по исправленной формуле для
всех бумаг с амортизацией.

## Критический баг: coupons/amortizations "замерзали" после первой строки (миграция 006)

Найдено по вашему прямому сообщению: таблицы `coupons`/`amortizations`
переставали обновляться. Причина — связка двух решений в
`BondizationImporter`, не связанная с QA.md напрямую:

1. **Отбор "что обрабатывать сегодня"** был вида `LEFT JOIN coupons c ...
   WHERE c.id IS NULL` — буквально "нет вообще ни одной строки". Как
   только у бумаги появлялась хотя бы одна строка (из сотен нужных),
   бумага навсегда выпадала из ежедневной обработки.
2. **`value_per_bond NOT NULL`** заставлял тихо пропускать (`continue`)
   любую выплату, для которой API ещё не знает сумму — типично для
   флоатеров и структурных облигаций (будущая сумма купона зависит от ещё
   не наступившей даты фиксации базовой ставки). Строка при этом не
   создавалась вообще, не как `NULL`, а как отсутствующий факт.

Вместе: у такой бумаги первая же прошедшая (уже известная) выплата
блокировала бумагу от дальнейшей обработки навсегда, а её же будущие
выплаты с ещё неизвестной суммой никогда не попадали в таблицу.

**Исправлено (миграция `006_coupons_amortizations_upsert.sql` +
переписанный `BondizationImporter`):**
- `coupons.value_per_bond` и `amortizations.value_per_bond` теперь
  `NULL`able. Строка вставляется, если у выплаты известна дата — сумма
  и ставка необязательны (вместо `continue` — `status='planned'`,
  `rate_percent`/`value_per_bond = NULL`).
- `coupon_number` (порядковый номер, который мы считали сами, а не брали
  из API) убран из схемы вместе со своим `UNIQUE KEY`. Вместо него —
  естественный ключ `UNIQUE (security_id, period_end_date)` для `coupons`
  и `UNIQUE (security_id, payment_date_planned)` для `amortizations`.
- `DELETE FROM ... WHERE security_id = ...` перед `INSERT` заменён на
  `INSERT ... ON DUPLICATE KEY UPDATE` — исходная причина держать
  DELETE+INSERT (нестабильность порядковых номеров между прогонами)
  больше не существует, раз ключ — это дата, а не искусственный счётчик.
- Отбор "что обрабатывать сегодня" (`importForAllPending`) теперь смотрит
  не на факт существования строк, а на факт незаполненности:
  - вообще ни одной строки в `coupons` ещё нет (первый сев — единственный
    случай, где для `coupons` критерий смотрит на факт существования, а
    не на содержимое: настоящий `zero_coupon` даёт пустой график законно,
    отличить это от "ещё не сеяли" без строк нельзя, поэтому такая бумага
    будет лишний раз открываться на bondization каждый день — безвредно,
    просто один лишний HTTP-запрос);
  - ИЛИ есть купон с известной датой, но `value_per_bond IS NULL`;
  - ИЛИ бумага уже отмечена `is_amortized=1` И есть амортизация с
    известной датой, но `value_per_bond IS NULL`. Проверяется только для
    уже-амортизируемых бумаг намеренно: у подавляющего большинства бумаг
    `amortizations` пуста НАВСЕГДА (обычный bullet-бонд) — если бы
    отсутствие строк в `amortizations` само по себе считалось "нужно
    обработать", это означало бы пересев всего рынка каждый день.

Проверено локально (MySQL 8, `FakeIssClient`): симуляция "день 1 / день
2" — бумага с плейсхолдер-купоном (дата известна, сумма нет) корректно
переоткрывается на день 2 и апсертится в ту же строку (не дублируется),
а полностью заполненная бумага на день 2 не переоткрывается вообще
(bondization-эндпоинт для неё не вызывается).

**Действие на сервере (обязательно, разово):** после `006` прогнать
`php bin/seed_bondization.php --force` один раз — это пересеет график
для ВСЕХ активных бумаг под новой логикой, включая те, что уже "замёрзли"
с первой строки. Дальше обычный (без `--force`) режим по расписанию
корректно донаполняет только реально незаполненные бумаги.

## Требует диагностики на боевой БД (SQL для запуска пользователем)

Важная оговорка: `securities` хранит только выведенные `coupon_type`/
`is_structured`, а не сырой текст `BOND_TYPE` — напрямую сгруппировать по
исходной формулировке тега в БД нельзя (в QA.md запрос `GROUP BY
BOND_TYPE` предполагал такую колонку, которой в схеме нет). Что можно
посчитать уже сейчас через уже сохранённые поля:

```sql
-- 1) сколько бумаг ушло в unknown, в разрезе типа и уровня листинга
SELECT security_type, listing_level, COUNT(*) AS cnt
FROM securities
WHERE coupon_type = 'unknown'
GROUP BY security_type, listing_level
ORDER BY cnt DESC;

-- 2) coupon_frequency IS NULL — коррелирует ли с уже прошедшим погашением
SELECT
    CASE WHEN maturity_date < CURDATE() THEN 'уже погашена' ELSE 'ещё торгуется' END AS bucket,
    COUNT(*) AS cnt
FROM securities
WHERE coupon_frequency IS NULL
GROUP BY bucket;

-- 3) то же самое, дополнительно разрезая по is_structured —
--    гипотеза QA.md: структурные облигации могут не иметь
--    coupon_frequency по отдельной причине, не связанной с погашением
SELECT
    CASE WHEN maturity_date < CURDATE() THEN 'уже погашена' ELSE 'ещё торгуется' END AS bucket,
    is_structured,
    COUNT(*) AS cnt
FROM securities
WHERE coupon_frequency IS NULL
GROUP BY bucket, is_structured;

-- 4) is_mortgage_backed — сколько нашлось после миграции 005 + повторного
--    прогона seed_market.php
SELECT COUNT(*) FROM securities WHERE is_mortgage_backed = 1;

-- 5) has_offer (текущая гипотеза BUYBACKDATE-only) — сколько бумаг попало
SELECT COUNT(*) FROM securities WHERE has_offer = 1;
```

Если пункт 1 (SQL по сырому `BOND_TYPE`) вам важен именно с текстом тега —
проще всего временно раскомментировать вывод `BOND_TYPE` в
`bin/debug_iss_security.php` на конкретных ISIN из выборки `unknown`, как
делали раньше в первом этапе, а не заводить для этого отдельное хранимое
поле в БД (сырой `BOND_TYPE` сейчас нигде не сохраняется, только его
интерпретация).

## Требует проверки живым ISS API (через `bin/debug_iss_security.php` или curl)

Всё из ISS у меня нет сетевого доступа проверить самому — нужен запуск на
вашей стороне:

1. **`BONDTYPE`/`BONDSUBTYPE`/`ZSPREAD`** — есть ли эти поля в ответе
   `/iss/securities/{SECID}.json` для произвольной облигации. Если да —
   это готовая структурированная классификация вместо угадывания по
   ключевым словам в `BOND_TYPE`, закрывает сразу несколько вопросов
   (`coupon_type=unknown`, `security_type`, возможно `floater_spread_percent`
   через `ZSPREAD`).
2. **`OFFERDATE`** — в ответе доска-специфичного эндпоинта
   (`/iss/engines/stock/markets/bonds/boards/{BOARD}/securities/{SECID}.json`,
   тот же, что уже даёт `COUPONVALUE`/`NEXTCOUPON`/`ACCRUEDINT`), на бумаге
   с заведомо активной офертой. Сравнить с `BUYBACKDATE` этой же бумаги —
   синхронны ли они. От результата зависит, стоит ли код `has_offer`
   переписывать под `OR OFFERDATE IS NOT NULL` (новый HTTP-запрос) или
   `BUYBACKDATE` уже достаточен.
3. **`DEFAULT_STATE`** — на реальном ISIN в техдефолте. Если поле рабочее
   («Y»/«N»), это прямой сигнал для будущего событийного детектора
   дефолтов вместо самостоятельной сборки статуса из нескольких эвристик.

## Открытые решения (нужен ваш выбор)

Вынесены отдельным вопросом в чат (не блокируют остальную работу):

1. **`initial_issue_volume`** — семантика: `ISSUESIZE` подтверждённо в
   штуках, не в деньгах, а имя колонки подразумевает деньги.
2. **`is_high_yield`** — формула по ключевой ставке ЦБ vs сверка с
   индексом MOEX (`RUCBHYTR`/`RUEYBCSTR`/`RUGROWTR`) vs оба варианта.
3. **`offer_type` (put/call)** — частично закрыто: `OffersImporter`
   определяет его бесплатно через `PUTOPTIONDATE`/`CALLOPTIONDATE`
   доска-специфичного эндпоинта ISS API (см. раздел "offers — импортёр
   готов" выше), без RusBonds. Открыт только случай, когда оба поля
   пусты или оба заполнены — там честно остаётся `'unknown'`; нужно
   посмотреть по итогам боевого прогона на всём рынке, сколько таких
   случаев и стоит ли для них подключать RusBonds-скрейпинг.
4. **DaData (ОГРН/ОКВЭД/полное-краткое имя)** — регистрация и старт
   обогащения. Отдельно: скрипт `bin/enrich_issuers_dadata.php` +
   `src/DaData/*`, упомянутый в QA.md как «уже готов и передан отдельно»,
   **в этом репозитории не существует** — если решаем делать, пишем с
   нуля.

Первый этап (`README.md`) закрыл базовый импорт: 3061/3061 бумаг, 495
эмитентов, купоны и амортизации. Этот файл фиксирует выводы и решения по
дальнейшему разбору пропусков в `issuers`/`securities` — по мотивам
`documents/2026.08.10_BondKeeper_issuers_securities_QA.md`. Формат —
кратко, по каждому полю: что сделано / что нужно от пользователя / что

## Три находки в redemptions/is_amortized (миграция 007)

По вашему прямому разбору — три отдельных, но связанных бага в
`SecuritiesImporter`/`BondizationImporter`.

**1. Дата погашения в `redemptions` считалась неизменной навсегда.**
`upsertScheduledRedemption` проверял только факт существования строки —
если она уже была, повторный `MATDATE` молча игнорировался, даже если
реально изменился (досрочное погашение, реструктуризация). Исправлено:
теперь сравнивается `redemptions.payment_date_planned` с текущим
`MATDATE`; если совпадают — строка не трогается вообще (в т.ч.
`value_per_bond`, который мог уже скорректировать `BondizationImporter`
под остаток после амортизации); если не совпадают — обновляется ТОЛЬКО
дата.

**2. `redemptions.value_per_bond` считался с двойным вычетом амортизации.**
Формула была `securities.nominal_value − SUM(вся амортизация)`, где
`nominal_value` — текущий, живой номинал (тот же `FACEVALUE`, что
синкается ежедневно и у амортизируемой бумаги УЖЕ САМ ПО СЕБЕ является
остатком после прошлых амортизаций), а `SUM` — по ВСЕЙ амортизации сразу
(bondization отдаёт график целиком, прошлые и будущие транши). Прошлая
амортизация вычиталась дважды (неявно — её уже нет в `FACEVALUE`, и явно —
она есть в сумме), плюс вычиталась вся ещё не наступившая будущая. У
бумаги с существенной историей амортизации итог легко уходил в минус.

Исправлено добавлением новой колонки `securities.initial_nominal_value`
(миграция `007`) — номинал на момент выпуска, зафиксированный один раз при
первой вставке строки (`firstPresent(['INITIALFACEVALUE', 'FACEVALUE'])`,
приоритет обратный тому, что у `nominal_value`) и НЕ входящий в
`ON DUPLICATE KEY UPDATE` — по тому же принципу, что и `created_at`.
Формула теперь: `initial_nominal_value − SUM(вся амортизация)`, вычитается
ровно один раз из неизменной базы. Заодно сумма амортизации в
`adjustScheduledRedemption` теперь считается запросом `SUM(...)` к самой
таблице `amortizations`, а не по строкам из текущего HTTP-ответа — так
пересчёт остаётся корректным, даже если конкретный сегодняшний ответ API
неполный (см. пункт 3).

**3. `is_amortized` мог тихо и навсегда стать `FALSE` из-за разового сбоя
ответа API.** Сценарий: у бумаги реально есть амортизация, но в
конкретный день bondization-эндпоинт вернул купоны полностью, а блок
`amortizations` — пустым (тот же класс сбоя, что уже случался на 435
бумагах за один день). Раньше код писал `is_amortized = 0` при любом
пустом ответе — бумага теряла флаг навсегда, а вместе с ним переставала
даже ПРОВЕРЯТЬСЯ на предмет "не пришла ли амортизация" в pending-отборе
(флаг участвует в самом условии отбора).

Исправлено двумя взаимодополняющими правками:
- `is_amortized` в `BondizationImporter` теперь монотонный — пишется
  ТОЛЬКО в `TRUE` (по факту реально вставленных строк), никогда обратно
  в `FALSE`.
- `SecuritiesImporter` независимо выставляет тот же флаг спекулятивно —
  по ключевому слову "амортизир" в `BOND_TYPE` (тот же приём, что уже
  использован для `is_structured`/`is_mortgage_backed`), ДО того, как
  `BondizationImporter` вообще увидит хоть одну строку. Пишется через
  `GREATEST(is_amortized, VALUES(is_amortized))` в `ON DUPLICATE KEY
  UPDATE` — монотонный OR, а не перезапись, поэтому текстовый сигнал
  может только включить флаг, никогда не выключить то, что уже
  подтвердил `BondizationImporter` реальными строками.
- Pending-отбор `importForAllPending()` расширен: теперь для
  `is_amortized = 1` бумаг переоткрывает их и в случае, если
  `amortizations` пуста ВООБЩЕ (не только когда есть незаполненный
  плейсхолдер) — именно это закрывает сценарий выше: текстовый сигнал
  включил флаг раньше, чем появились реальные строки, поэтому одного
  "плейсхолдер существует" было бы недостаточно.

Проверено локально (MySQL 8, `FakeIssClient`) полным двухдневным
сценарием: смена `MATDATE`, попытка перезаписать `INITIALFACEVALUE` вторым
прогоном (не сработала — колонка осталась исходной), и Ромашка-1 —
бумага с `BOND_TYPE = "Амортизируемые облигации"`, у которой на первый
день `amortizations` пришла пустой, а `is_amortized` всё равно стало
`TRUE` сразу после `seed_market.php` и осталось `TRUE` после пустого
bondization-ответа; на второй день бумага корректно переоткрылась и
получила реальную строку амортизации.

**Важный нюанс при накатке на уже заполненную БД (весь текущий рынок,
~3061 бумага, уже сидировался ДО этой миграции).** Просто исключить
`initial_nominal_value` из `ON DUPLICATE KEY UPDATE` (как задумывалось по
аналогии с `created_at`) для уже существующих строк не сработало бы —
`ON DUPLICATE KEY UPDATE` трогает только перечисленные там колонки, и
поле осталось бы `NULL` навсегда для всех, кто был в базе до миграции.
Заменил на `initial_nominal_value = COALESCE(initial_nominal_value,
VALUES(initial_nominal_value))`: для уже заполненной строки — не трогает
(старое значение побеждает); для строки, где поле ещё `NULL` (все текущие
3061 бумаги на первый постмиграционный прогон) — заполняет сегодняшним
значением из API один раз, дальше не трогает. `INITIALFACEVALUE` по
спецификации ISS — номинал на момент выпуска, сам по себе не меняется со
временем, поэтому даже "запоздалое" первое чтение для бумаги, уже давно
торгующейся и прошедшей часть амортизации, должно корректно вернуть
историческое значение, а не сегодняшний слепок.

**Действие на сервере:** накатить `007_initial_nominal_value.sql`, затем
обычный `php bin/seed_market.php` (без флагов — заполнит
`initial_nominal_value` для всех уже существующих бумаг за счёт
COALESCE-бэкфилла выше), затем `php bin/seed_bondization.php --force` —
пересчитает `redemptions.value_per_bond` уже по исправленной формуле для
всех бумаг с амортизацией.

## Критический баг: coupons/amortizations "замерзали" после первой строки (миграция 006)

Найдено по вашему прямому сообщению: таблицы `coupons`/`amortizations`
переставали обновляться. Причина — связка двух решений в
`BondizationImporter`, не связанная с QA.md напрямую:

1. **Отбор "что обрабатывать сегодня"** был вида `LEFT JOIN coupons c ...
   WHERE c.id IS NULL` — буквально "нет вообще ни одной строки". Как
   только у бумаги появлялась хотя бы одна строка (из сотен нужных),
   бумага навсегда выпадала из ежедневной обработки.
2. **`value_per_bond NOT NULL`** заставлял тихо пропускать (`continue`)
   любую выплату, для которой API ещё не знает сумму — типично для
   флоатеров и структурных облигаций (будущая сумма купона зависит от ещё
   не наступившей даты фиксации базовой ставки). Строка при этом не
   создавалась вообще, не как `NULL`, а как отсутствующий факт.

Вместе: у такой бумаги первая же прошедшая (уже известная) выплата
блокировала бумагу от дальнейшей обработки навсегда, а её же будущие
выплаты с ещё неизвестной суммой никогда не попадали в таблицу.

**Исправлено (миграция `006_coupons_amortizations_upsert.sql` +
переписанный `BondizationImporter`):**
- `coupons.value_per_bond` и `amortizations.value_per_bond` теперь
  `NULL`able. Строка вставляется, если у выплаты известна дата — сумма
  и ставка необязательны (вместо `continue` — `status='planned'`,
  `rate_percent`/`value_per_bond = NULL`).
- `coupon_number` (порядковый номер, который мы считали сами, а не брали
  из API) убран из схемы вместе со своим `UNIQUE KEY`. Вместо него —
  естественный ключ `UNIQUE (security_id, period_end_date)` для `coupons`
  и `UNIQUE (security_id, payment_date_planned)` для `amortizations`.
- `DELETE FROM ... WHERE security_id = ...` перед `INSERT` заменён на
  `INSERT ... ON DUPLICATE KEY UPDATE` — исходная причина держать
  DELETE+INSERT (нестабильность порядковых номеров между прогонами)
  больше не существует, раз ключ — это дата, а не искусственный счётчик.
- Отбор "что обрабатывать сегодня" (`importForAllPending`) теперь смотрит
  не на факт существования строк, а на факт незаполненности:
  - вообще ни одной строки в `coupons` ещё нет (первый сев — единственный
    случай, где для `coupons` критерий смотрит на факт существования, а
    не на содержимое: настоящий `zero_coupon` даёт пустой график законно,
    отличить это от "ещё не сеяли" без строк нельзя, поэтому такая бумага
    будет лишний раз открываться на bondization каждый день — безвредно,
    просто один лишний HTTP-запрос);
  - ИЛИ есть купон с известной датой, но `value_per_bond IS NULL`;
  - ИЛИ бумага уже отмечена `is_amortized=1` И есть амортизация с
    известной датой, но `value_per_bond IS NULL`. Проверяется только для
    уже-амортизируемых бумаг намеренно: у подавляющего большинства бумаг
    `amortizations` пуста НАВСЕГДА (обычный bullet-бонд) — если бы
    отсутствие строк в `amortizations` само по себе считалось "нужно
    обработать", это означало бы пересев всего рынка каждый день.

Проверено локально (MySQL 8, `FakeIssClient`): симуляция "день 1 / день
2" — бумага с плейсхолдер-купоном (дата известна, сумма нет) корректно
переоткрывается на день 2 и апсертится в ту же строку (не дублируется),
а полностью заполненная бумага на день 2 не переоткрывается вообще
(bondization-эндпоинт для неё не вызывается).

**Действие на сервере (обязательно, разово):** после `006` прогнать
`php bin/seed_bondization.php --force` один раз — это пересеет график
для ВСЕХ активных бумаг под новой логикой, включая те, что уже "замёрзли"
с первой строки. Дальше обычный (без `--force`) режим по расписанию
корректно донаполняет только реально незаполненные бумаги.

## Уже сделано в коде (миграция 005 + `SecuritiesImporter`)

Все четыре пункта ниже — без новых HTTP-запросов, из уже вызываемых
эндпоинтов. Проверено локально на MySQL 8 через `FakeIssClient`-двойник.

1. **`trading_start_date`.** Читается `ISSUEDATE`, при отсутствии —
   `STARTDATEMOEX`, из уже парсящегося `description`-блока. Ранее поле
   физически приходило в ответе, но не читалось кодом.
2. **`security_type`.** Читается `type` из `/iss/securities.json?q=` (тот
   же поиск, что даёт `emitent_inn`). Маппинг на текущий ENUM схемы
   (`corporate`/`ofz`/`municipal`/`short_term`):
   `ofz_bond` → `ofz`; `subfederal_bond`/`municipal_bond` → `municipal`;
   всё остальное (`corporate_bond`, `exchange_bond`, `cb_bond`,
   `euro_bond`, `ifi_bond`) → `corporate`. Упрощение осознанное — в схеме
   нет более узких категорий под евробонды/облигации МФО и т.п.; `short_term`
   импортёром не выставляется вообще — среди значений `type` нет прямого
   соответствия. Если понадобится точнее — расширять ENUM отдельным
   решением, не сейчас.
3. **`has_offer`.** Первый сигнал — `BUYBACKDATE` из description-блока
   (`has_offer = BUYBACKDATE IS NOT NULL`). **Это не финальная логика** —
   QA.md указывает на второй, независимый источник (`OFFERDATE` из
   доска-специфичного marketdata-эндпоинта, который импортёр пока не
   запрашивает) и на то, что синхронность полей не проверена вживую. См.
   открытый пункт ниже.
4. **`is_mortgage_backed`** (новая колонка, миграция `005`). `TRUE`, если
   `BOND_TYPE` содержит «ипотечн» или имя эмитента содержит «ипотечный
   агент» (стандартное имя SPV для ИЦБ ДОМ.РФ). Найдено на конкретном
   кейсе `RU000A0JQAM6` — у таких бумаг **не может быть** полного графика
   купонов вперёд (купон = фактические поступления по ипотечному пулу),
   это не пробел импорта. Флаг — чтобы продукт не показывал пользователю
   пустой график как сломанный.

## Исправление одной неточности в QA.md

**`coupon_type = zero_coupon`.** QA.md предположил, что это значение
ставится по факту (пустой массив `coupons` в bondization), а не по
ключевому слову. Проверено по коду `SecuritiesImporter::mapCouponType()`:
на самом деле это **чисто текстовая проверка** — ключевые слова «дисконт»
/ «без купон» в `BOND_TYPE`, ровно тот же механизм, что и у `floating`/
`indexed`/`fixed`. Фактическая логика (пустой bondization) нигде не
используется. Отдельно менять не стали — как определение термина в
QA.md сформулировано корректно, разошлось только предположение о
механизме; текстовый способ на практике работает (см. `README.md`,
разбор `BOND_TYPE`).

Также уточнение по `floater_base_rate`: в QA.md указано, что это «уже
посчитанное числовое значение базы» — но в реальной схеме
(`database/001_schema.sql`) это `ENUM('ruonia','key_rate','other')`, то
есть **название** базового индекса, а не число. Числовой спред — отдельно,
`floater_spread_percent`. Смены схемы не требуется, учитывать при будущем
парсере floaters.ru: нужно распознавать «КС» → `key_rate`, «RUONIA» →
`ruonia`.

## Требует диагностики на боевой БД (SQL для запуска пользователем)

Важная оговорка: `securities` хранит только выведенные `coupon_type`/
`is_structured`, а не сырой текст `BOND_TYPE` — напрямую сгруппировать по
исходной формулировке тега в БД нельзя (в QA.md запрос `GROUP BY
BOND_TYPE` предполагал такую колонку, которой в схеме нет). Что можно
посчитать уже сейчас через уже сохранённые поля:

```sql
-- 1) сколько бумаг ушло в unknown, в разрезе типа и уровня листинга
SELECT security_type, listing_level, COUNT(*) AS cnt
FROM securities
WHERE coupon_type = 'unknown'
GROUP BY security_type, listing_level
ORDER BY cnt DESC;

-- 2) coupon_frequency IS NULL — коррелирует ли с уже прошедшим погашением
SELECT
    CASE WHEN maturity_date < CURDATE() THEN 'уже погашена' ELSE 'ещё торгуется' END AS bucket,
    COUNT(*) AS cnt
FROM securities
WHERE coupon_frequency IS NULL
GROUP BY bucket;

-- 3) то же самое, дополнительно разрезая по is_structured —
--    гипотеза QA.md: структурные облигации могут не иметь
--    coupon_frequency по отдельной причине, не связанной с погашением
SELECT
    CASE WHEN maturity_date < CURDATE() THEN 'уже погашена' ELSE 'ещё торгуется' END AS bucket,
    is_structured,
    COUNT(*) AS cnt
FROM securities
WHERE coupon_frequency IS NULL
GROUP BY bucket, is_structured;

-- 4) is_mortgage_backed — сколько нашлось после миграции 005 + повторного
--    прогона seed_market.php
SELECT COUNT(*) FROM securities WHERE is_mortgage_backed = 1;

-- 5) has_offer (текущая гипотеза BUYBACKDATE-only) — сколько бумаг попало
SELECT COUNT(*) FROM securities WHERE has_offer = 1;
```

Если пункт 1 (SQL по сырому `BOND_TYPE`) вам важен именно с текстом тега —
проще всего временно раскомментировать вывод `BOND_TYPE` в
`bin/debug_iss_security.php` на конкретных ISIN из выборки `unknown`, как
делали раньше в первом этапе, а не заводить для этого отдельное хранимое
поле в БД (сырой `BOND_TYPE` сейчас нигде не сохраняется, только его
интерпретация).

## Требует проверки живым ISS API (через `bin/debug_iss_security.php` или curl)

Всё из ISS у меня нет сетевого доступа проверить самому — нужен запуск на
вашей стороне:

1. **`BONDTYPE`/`BONDSUBTYPE`/`ZSPREAD`** — есть ли эти поля в ответе
   `/iss/securities/{SECID}.json` для произвольной облигации. Если да —
   это готовая структурированная классификация вместо угадывания по
   ключевым словам в `BOND_TYPE`, закрывает сразу несколько вопросов
   (`coupon_type=unknown`, `security_type`, возможно `floater_spread_percent`
   через `ZSPREAD`).
2. **`OFFERDATE`** — в ответе доска-специфичного эндпоинта
   (`/iss/engines/stock/markets/bonds/boards/{BOARD}/securities/{SECID}.json`,
   тот же, что уже даёт `COUPONVALUE`/`NEXTCOUPON`/`ACCRUEDINT`), на бумаге
   с заведомо активной офертой. Сравнить с `BUYBACKDATE` этой же бумаги —
   синхронны ли они. От результата зависит, стоит ли код `has_offer`
   переписывать под `OR OFFERDATE IS NOT NULL` (новый HTTP-запрос) или
   `BUYBACKDATE` уже достаточен.
3. **`DEFAULT_STATE`** — на реальном ISIN в техдефолте. Если поле рабочее
   («Y»/«N»), это прямой сигнал для будущего событийного детектора
   дефолтов вместо самостоятельной сборки статуса из нескольких эвристик.

# Этап 4: событийный движок (MVP) + Telegram-бот — план

**Дата:** 4 сентября 2026. Источники данных для MVP — по прямому решению
пользователя: только **ФНС-блокировки** (`fns_blocks`) и **рейтинговые
действия** (`rating_actions`), без НРД/e-disclosure. Модель
пользователей — Telegram как первая и единственная точка входа
(`users.telegram_id`), watchlist — вручную через команды бота, в
уведомления идут только существенные события (не рутинные подтверждения
без изменений).

## Главная находка: движок уже спроектирован, просто не подключён

Схема `database/001_schema.sql` с самого первого дня проекта содержит
ПОЛНЫЙ "Кластер 2. Событийный движок" и "Кластер 3. Пользователи и
коммерция" — `event_types` (засеян таксономией A1–E3, 24 типа),
`raw_messages`, `event_stories`, `events`, `users` (уже с `telegram_id`,
`telegram_username`, `telegram_bot_blocked`), `tariffs` (уже засеян:
free/basic/pro/expert), `subscriptions`, `payments`, `watchlist`,
`notifications`. `rating_actions.event_id` и `fns_blocks.event_id` —
тоже с самого начала, просто ВСЕГДА NULL: ни один импортёр ни разу не
создал ни одной строки в `events`. Первоисточник схемы —
`documents/2026.08.08_bondkeeper_schema_v2.sql` (сверил построчно, живая
`001_schema.sql` совпадает).

**Значит, это НЕ проектирование архитектуры с нуля** — она уже есть и
проверена на бумаге, эта задача — реализовать код поверх неё. Никаких
новых миграций для событий/пользователей/уведомлений не требуется.

Нужные для MVP типы событий (уже в `event_types`):

| code | Название | primary_source | default_priority | notify_client |
|---|---|---|---|---|
| C5 | Рейтинговое действие | rating_agency | yellow | TRUE |
| E1 | Блокировка счетов ФНС | fns | yellow | TRUE |

(E3 "Каскад по эмитенту" — `is_derived=TRUE`, требует корреляции
нескольких событий одного эмитента — сознательно вне MVP, см. "Дальше,
не сейчас" в конце.)

## Принципиальное решение: где рождается событие

Событие создаётся **в момент, когда код и так уже знает "было/стало"**
— не отдельным опросом-диффом снапшотов, а прямо внутри уже
существующих импортёров, которые читают старое значение ПЕРЕД записью
нового (тот же приём, что уже есть в `CurrentRatingsSync`/
`FnsBlocksImporter::applyResult()` для `unblock_date`).

**Только импортёры уровня "действие" создают события** — не "снимок
текущего состояния":
- `rating_actions` (через `RatingActionsWriter`) — да, там уже есть
  `rating_from`/`rating_to`/`outlook_from`/`outlook_to`, всё нужное для
  решения "существенно или нет" передаётся туда же.
- `fns_blocks` (через `FnsBlocksImporter`) — да, добавляем чтение
  состояния ДО записи.
- `NkrImporter`/`ExpertRaImporter`/`AcraImporter`/`ManualRatingsImporter`
  (полная периодическая выгрузка `current_ratings`, не из новостей) —
  **НЕТ**, они не создают события. Иначе один и тот же реальный
  рейтинговый релиз задвоится: сначала событие от новостного импортёра,
  потом ещё одно от следующего планового полного прогона, увидевшего то
  же самое изменение в `current_ratings`. Полные импортёры остаются тем,
  чем и были — сверкой/бэкстопом кэша, не источником событий.

**Уточнение при реализации (см. "Что изменилось при реализации" в конце
файла):** на момент написания этого плана АКРА ещё не имела рабочего
новостного импортёра вообще — предполагалось, что события по ней
появятся не раньше, чем заработает почтовый `AcraMailImporter` (ждём
почтовый ящик). К моменту реализации Фазы 1 это уже устарело: параллельно
был построен `AcraNewsImporter` (парсинг `/press-releases/` на сайте
АКРА, живьём подтверждено — WAF блокирует только `/ratings/issuers/`,
не раздел новостей) и уже работает в проде каждые 30 минут. Он тоже
проводит запись через `RatingActionsWriter`, поэтому события C5 по АКРА
пошли АВТОМАТИЧЕСКИ, без отдельной работы — почтовый `AcraMailImporter`
для этого не понадобился.

## Фильтр существенности — УТОЧНЕНО пользователем (4 сентября 2026)

**C5 (рейтинговое действие) — фильтра НЕТ вообще.** Пользователь прямо
решил: уведомлять о ЛЮБОМ рейтинговом действии по эмитенту из watchlist,
включая обычное "подтверждено, без изменений" (грейд и прогноз те же).
Первоначальный план (пропускать рутинные подтверждения) — ОТМЕНЁН. Раз
каждая строка `rating_actions`, дошедшая до `RatingActionsWriter::upsert()`,
уже прошла все проверки самого импортёра (глагол/грейд распознаны,
эмитент сопоставлен) — событие создаётся всегда, без доп. условий.

**E1 (блокировка ФНС) — три конкретных триггера** (тоже уточнено
пользователем, каждый — отдельное уведомление с своим текстом):

1. **Начало блокировки** (`is_fns_blocked` 0→1, либо строки для
   эмитента в `fns_blocks` ещё не было вообще) — в уведомлении: сумма
   (`blocked_amount`), число заблокированных банков (`active_bank_count`),
   дата начала блокировки.
2. **Изменение суммы блокировки** (`blocked_amount` изменился, при
   этом `is_fns_blocked` остаётся 1 — блокировка не начинается и не
   заканчивается, просто меняется цифра) — отдельное уведомление именно
   про это.
3. **Снятие блокировки** (`is_fns_blocked` 1→0) — в уведомлении: дата
   снятия.

Неуспешная проверка (`verification='error'`, капча/сеть) — НЕ событие
ни в одном из трёх случаев: мы не УЗНАЛИ ничего нового, а не
подтвердили отсутствие блокировки.

**Решено 4 сентября 2026, ПЕРЕСМОТРЕНО 17 сентября 2026:** изначально
изменение ТОЛЬКО `active_bank_count` (число банков) без изменения суммы
считалось неважным клиенту и событием не было. Пользователь прямо
попросил пересмотреть это — теперь это **четвёртый триггер**,
`kind='count_changed'` (только когда сумма НЕ менялась — при
одновременном изменении суммы И числа банков приоритет у
`amount_changed`, чтобы одно и то же реальное изменение не порождало два
разных уведомления подряд). Событие E1 создаётся по 4 триггерам
(начало/сумма/число банков/снятие).

**Честная оговорка по "дата-время"** — источник (service.nalog.ru) отдаёт
дату начала блокировки БЕЗ времени (`DATABEGIN`/`DATA` — формат
"ДД.ММ.ГГГГ", ни разу не встречалось со временем суток, см.
`FnsBlocksImporter::parseDate()`). Значит "дата-время начала блокировки"
в уведомлении честно может быть только ДАТОЙ от ФНС — точное время суток
взять неоткуда, это не пробел кода, а ограничение источника. Дата
СНЯТИЯ — ещё более приблизительная: `unblock_date` в БД — это день,
КОГДА МЫ ЭТО ЗАМЕТИЛИ (`CURDATE()` в момент успешной проверки), а не
день, когда блокировку реально сняла ФНС (между проверками эмитента
могут проходить дни — `bin/check_fns_blocks.php` по умолчанию проверяет
маленькими пачками, не каждый день всех). Можем честно показывать это
как "по состоянию на день последней проверки", но не как точную дату
снятия, если проверки нечастые.

## Новый класс: `src/Events/EventPublisher.php`

Общая точка входа для обоих источников (по аналогии с
`RatingActionsWriter`/`RatingNewsLog` — один класс, не дублировать в
каждом импортёре):

```php
final class EventPublisher
{
    public function __construct(private readonly PDO $db) {}

    /**
     * C5. Вызывается из RatingActionsWriter::upsert() сразу после
     * успешного апсерта, теми же значениями, что уже переданы туда —
     * ничего заново не запрашивать. Фильтра существенности НЕТ (решение
     * пользователя) — событие создаётся ВСЕГДА, в т.ч. на "подтверждено
     * без изменений". Возвращает int (не nullable) — единственная
     * причина не создать событие тут была бы ошибка записи, не бизнес-
     * логика.
     */
    public function publishRatingAction(
        int $issuerId,
        string $agency,
        string $actionDate,
        ?string $ratingFrom,
        string $ratingTo,
        ?string $outlookFrom,
        ?string $outlookTo,
        ?string $sourceUrl,
        ?string $sourceTitle,
    ): ?int { /* ... */ }

    /**
     * E1. Вызывается из FnsBlocksImporter::applyResult() — на входе уже
     * известны И старое (прочитанное ДО апсерта), И новое состояние.
     * Различает 4 триггера пользователя через payload_json.kind:
     * 'started' (0→1), 'amount_changed' (остаётся 1, сумма другая),
     * 'count_changed' (остаётся 1, сумма та же, число банков другое —
     * добавлено 17 сентября 2026), 'lifted' (1→0). Ни один из четырёх не
     * наступил (например, повторное подтверждение той же суммы/банков) —
     * возвращает null, событие не создаётся. $oldBlockedAmount/
     * $newBlockedAmount — строками (тот же формат, что в
     * fns_blocks.blocked_amount, сравнение как строк безопасно — обе
     * стороны из одного и того же parseAmount()).
     */
    public function publishFnsBlockChange(
        int $issuerId,
        bool $oldBlocked,
        ?string $oldBlockedAmount,
        int $oldActiveBankCount,
        bool $newBlocked,
        ?string $newBlockedAmount,
        int $newActiveBankCount,
        string $blockDate,
        ?string $reason,
        ?string $sourceReference,
    ): ?int { /* ... */ }
}
```

Внутри каждого метода — одна транзакция:
1. `INSERT INTO raw_messages (source, source_ref, raw_payload, processing_status)`
   — `source='rating_agency'`/`'fns'`, `raw_payload` = JSON со всеми
   входными полями (то же "сырьё", что уже разобрано выше по цепочке —
   честная запись, что легло в основу события, для аудита).
2. `INSERT INTO events (issuer_id, event_type_code, event_date, published_at,
   priority, payload_json, raw_message_id)` — `priority` = `event_types.default_priority`
   для MVP (без хитрой эскалации по силе действия — сознательно просто,
   правки приоритета поштучно — это уже "не MVP", см. ниже).
3. Обновить `rating_actions.event_id`/`fns_blocks.event_id` на ID
   только что созданной строки (FK для этого и существует).

## Интеграция в существующий код — точечно, не переписывать импортёры

- **`RatingActionsWriter::upsert()`** — единственное место, которое
  должно порождать C5 для ВСЕХ агентств, добавить вызов
  `EventPublisher::publishRatingAction()` последним шагом, после своего
  `INSERT ... ON DUPLICATE KEY UPDATE`. `RatingActionsWriter` получает
  `EventPublisher` через конструктор (как и `PDO` сейчас). **Важно**
  (см. "Что изменилось при реализации"): на момент написания плана
  предполагалось, что НКР/НРА/Эксперт РА все трое уже проводят запись
  через этот класс — на практике НРА (`NraImporter`) дублировала
  собственный `INSERT INTO rating_actions` в обход него. Раз
  `RatingActionsWriter` — единственная точка публикации C5, НРА нужно
  ПЕРЕВЕСТИ на `RatingActionsWriter::upsert()`, иначе она тихо останется
  без событий вообще.
- **`FnsBlocksImporter::applyResult()`** — перед началом транзакции
  добавить `SELECT is_fns_blocked, active_bank_count FROM fns_blocks
  WHERE issuer_id = ?` (старое состояние; отсутствие строки = "было
  false/0"), после успешного апсерта — вызвать
  `EventPublisher::publishFnsBlockChange()` с обоими состояниями, а
  затем — если вернулся не-`null` id — отдельным `UPDATE fns_blocks SET
  event_id = ? WHERE issuer_id = ?` (симметрично тому, что делает
  `RatingActionsWriter::upsert()` для `rating_actions.event_id`; легко
  забыть, потому что `EventPublisher` сам ничего не пишет обратно в
  таблицу-источник — см. "Что изменилось при реализации").
  `FnsBlocksImporter` тоже получает `EventPublisher` через конструктор.
- Все импортёры, где их создают (`bin/seed_ratings.php`,
  `bin/check_fns_blocks.php`, `bin/daemon_nkr_news.php`,
  `bin/daemon_expert_ra_news.php`, `bin/daemon_nra.php`) — добавить один
  `new EventPublisher($db)` и передать в конструктор.

## Telegram-бот

**Предварительное условие (на стороне пользователя, не могу сделать
сам):** создать бота через `@BotFather` в Telegram, получить токен.
Хранить в `config/telegram_bot.php` (тот же принцип, что
`config/acra_mailbox.php` — секрет отдельно от кода, файл в
`.gitignore`, коммитится только `.example.php`).

**Long polling, не webhook** — для MVP проще: не нужен публичный
HTTPS-сервер/сертификат, вписывается в уже существующий паттерн
`bin/daemon_*.php` (цикл с `sleep`). Вебхук — естественная миграция
позже, когда появится веб-сервер под остальной продукт.

Новые классы:
- **`src/Telegram/TelegramClient.php`** — тонкая обёртка над Bot API:
  `getUpdates(int $offset): array`, `sendMessage(int $chatId, string $text): bool`.
  Курлом, тот же стиль, что `RatingsHttp`.
- **`src/Telegram/BotCommandHandler.php`** — разбирает входящие команды
  из `getUpdates()`:
  - `/start` — `INSERT ... ON DUPLICATE KEY UPDATE` в `users` по
    `telegram_id` (регистрация или "снова живой", если раньше
    `telegram_bot_blocked=TRUE` — сбросить флаг). Заодно — если у
    пользователя ещё нет ни одной строки в `subscriptions`, создать
    `tariff_code='free'`, `status='active'`, `current_period_end='9999-12-31'`
    (по комментарию в самой схеме — так уже задуман sentinel для
    бессрочных). **Платежи/апгрейд тарифа — вне этого MVP**, только
    соблюдение лимита `free.max_tracked_issuers = 3`.
  - `/watch <название или ИНН>` — `IssuerMatcher::findIssuerIdByName()`/
    `findIssuerIdByInn()` (тот же класс, что уже everywhere), проверка
    лимита тарифа (`COUNT(DISTINCT issuer_id) FROM watchlist WHERE user_id=?`
    против `tariffs.max_tracked_issuers` активной подписки), `INSERT INTO
    watchlist`.
  - `/unwatch <название>`, `/list` (показать watchlist), `/help`.
- **`bin/daemon_telegram_bot.php`** — цикл: короткий интервал (2-3 сек)
  опрашивает `getUpdates` (реакция на команды почти мгновенная), раз в
  30-60 сек — отдельный проход "разослать новые события" (см. ниже).
  Тот же принцип чередования, что уже есть у `daemon_nkr_news.php`
  (частый/глубокий), просто здесь "частый" — команды, "редкий" —
  рассылка.

## Рассылка уведомлений

`SELECT` новых `events` (`notify_client=TRUE` у их `event_types`), у
которых ещё нет строки в `notifications` для кого-то из смотрящих:

```sql
SELECT DISTINCT w.user_id, e.id AS event_id
FROM events e
JOIN watchlist w ON w.issuer_id = e.issuer_id
LEFT JOIN notifications n ON n.event_id = e.id AND n.user_id = w.user_id AND n.channel = 'telegram'
JOIN event_types et ON et.code = e.event_type_code
WHERE et.notify_client = TRUE AND n.id IS NULL
```

Для каждой пары — `INSERT INTO notifications (..., status='queued')`
(UNIQUE KEY `(user_id, event_id, channel)` уже защищает от дублей, если
цикл рассылки почему-то пройдёт по тому же событию дважды), затем сразу
`sendMessage()`, по результату — `UPDATE notifications SET status='sent'/'failed', sent_at=NOW()`.
Если Telegram вернул "Forbidden: bot was blocked by the user" —
`UPDATE users SET telegram_bot_blocked = TRUE`, дальше этому
пользователю не слать, пока не напишет боту снова (тогда `/start`
сбросит флаг).

**Шаблоны сообщений** (по `event_type_code` + `payload_json.kind` для E1,
читаются из `events.payload_json`; переписаны 17 сентября 2026 —
добавлен ИНН эмитента (кроме `lifted`, по образцу пользователя), суммы —
через `BotFormatting::formatMoney()`, разделитель разрядов + "₽", тот же
формат, что и в разделе "Статус"; см. также `checkFnsOnAdd()` в
`BotCommandHandler` — отдельный, не через `events`/`notifications`, канал
для "текущий статус при добавлении эмитента", формат текста тот же, что
у `started`):
- C5 (всегда, включая "без изменений"): `🔔 <агентство>: <эмитент> — <было> → <стало>, прогноз: <outlook>. <ссылка на пресс-релиз>`
  (если `rating_from === rating_to` — явно писать "рейтинг подтверждён на уровне <X>", не подавать как "было X → стало X", чтобы не выглядело странно).
- E1 `kind='started'`: `⚠️ <эмитент> | ИНН <инн>: Блокировка счетов ФНС | Дата блокировки: <дата> | Количество заблокированных счетов: N | Заблокированная сумма: X ₽ | <причина>`
- E1 `kind='amount_changed'`: `⚠️ <эмитент> | ИНН <инн>: сумма блокировки ФНС изменилась — было X ₽, стало Y ₽ (заблокированных счетов: N).`
- E1 `kind='count_changed'` (новый, 17 сентября 2026): `⚠️ <эмитент> | ИНН <инн>: количество заблокированных счетов ФНС изменилось — было N, стало M.`
- E1 `kind='lifted'`: `✅ <эмитент>: блокировка счетов ФНС снята (по состоянию на <дата>).`

   10 эмитентов/14 дней (было 3/36500), таблицы `bot_dialog_state`/

3. **Рассылка** — ЗАВЕРШЕНО (8 сентября 2026). `src/Telegram/

## Что изменилось при реализации Фазы 1 (сентябрь 2026)

Планирование этого документа и сама реализация `EventPublisher` велись
двумя параллельными заходами (обычная практика в этом проекте — см.
похожие сверки в `docs/STAGE3_RATINGS.md`), и код, полученный из второго
захода, разошёлся с основной веткой в трёх местах — все найдены и
исправлены ДО того, как код лёг в основную ветку:

1. **`fns_blocks.event_id` не проставлялся.** Первая версия
   `FnsBlocksImporter::applyResult()` вызывала
   `EventPublisher::publishFnsBlockChange()`, но не делала обратный
   `UPDATE fns_blocks SET event_id = ...` — единственная причина, ради
   которой вообще читалось "было" ДО апсерта, оставалась неиспользованной
   по факту. Событие в `events` создавалось корректно, но связать его со
   строкой `fns_blocks` было нельзя (`event_id` так и оставался `NULL`
   навсегда) — то есть ИМЕННО то, что этот документ называет "итогом
   Фазы 1" ("`rating_actions.event_id`/`fns_blocks.event_id` наконец
   заполняются"), для `fns_blocks` не выполнялось. Офлайн-тест на SQLite
   этого не ловил, потому что тестировал `EventPublisher` напрямую, в
   обход `FnsBlocksImporter` (см. докблок `tests/test_event_engine.php`
   — MySQL-диалект `ON DUPLICATE KEY UPDATE` у SQLite не работает в
   принципе, это не пробел именно этого теста, а известная граница всего
   офлайн-тестирования проекта). Исправлено: `applyResult()` делает
   `UPDATE fns_blocks SET event_id = :event_id WHERE issuer_id = :issuer_id`
   сразу после успешной публикации, но ТОЛЬКО если она вернула не-`null`
   id (иначе, когда ни один из 3 триггеров не сработал, старое значение
   `event_id` не трогается, а не затирается `NULL`'ом).
2. **`NraImporter` дублировала `INSERT INTO rating_actions` в обход
   `RatingActionsWriter`.** Документ выше предполагал, что все три
   агентства (НКР/НРА/Эксперт РА) уже проводят запись через общий класс
   — на практике это было верно только для НКР/Эксперт РА (новостные
   импортёры), а `NraImporter` — единственный, кто пишет `rating_actions`
   из ПОЛНОЙ Excel-выгрузки, а не из ленты новостей — всегда делал свой
   собственный `INSERT ... ON DUPLICATE KEY UPDATE`, написанный ДО того,
   как `RatingActionsWriter` вообще появился как общий класс. Раз
   `EventPublisher::publishRatingAction()` подключён ИМЕННО в
   `RatingActionsWriter::upsert()` (единственная точка публикации C5) —
   НРА тихо осталась бы вообще без событий C5, при том что таблица типов
   событий выше явно включает НРА в MVP. Исправлено: `NraImporter`
   получает `RatingActionsWriter` через конструктор и вызывает
   `$this->writer->upsert(...)` вместо своего SQL — заодно устранена и
   сама изначальная цель, ради которой `RatingActionsWriter` создавался
   ("чтобы НРА и новостные парсеры не дублировали один и тот же SQL"),
   которая, как выяснилось, не была доведена до конца раньше.
3. **`bin/seed_ratings.php`/демоны основывались на снимке кода ДО
   `AcraNewsImporter`.** Пришедший код всё ещё ссылался на несуществующий
   `AcraMailImporter`/`AcraMailboxConfig` (планировался как решение для
   АКРА, когда предполагалось, что единственный путь — почтовая
   рассылка) и на несуществующий `bin/daemon_acra_news.php`. К этому
   моменту в основной ветке уже был готовый `AcraNewsImporter` (парсинг
   `/press-releases/`, живьём проверенный, работающий в проде каждые 30
   минут через обычный OS cron) — если бы файлы легли как есть, это
   ЗАМЕНИЛО бы рабочую боевую интеграцию АКРА на код, ссылающийся на
   несуществующие классы (`--agency=acra-news` перестал бы работать
   вообще). Исправлено: `AcraNewsImporter` оставлена как есть, в её
   конструктор `RatingActionsWriter` просто дополнительно получает
   `EventPublisher` — см. пункт про АКРА в "Принципиальное решение" выше.

Офлайн-тест (`tests/test_event_engine.php`) дополнен статической
проверкой (не поведенческой — SQLite не может исполнить MySQL-диалект
апсертов, см. п.1 выше): читает исходники `FnsBlocksImporter.php`/
`RatingActionsWriter.php`/`NraImporter.php` и проверяет, что нужные
`UPDATE ... SET event_id` и вызов `$this->writer->upsert(...)`
физически присутствуют в коде — дешёвая защита именно от повторения
находок 1 и 2 выше.

## Что изменилось при слиянии Фаз 2-3 (сентябрь 2026)

Тот же параллельный заход, что и у Фазы 1 (см. выше) — пакет с ботом и
рассылкой был подготовлен на основе `docs/STAGE4_EVENT_ENGINE.md` ДО
того, как в него попали правки из раздела "Что изменилось при
реализации Фазы 1" (та же причина расхождения, не новая). На сам код
бота/рассылки это не повлияло — `BotCommandHandler`/
`NotificationDispatcher` ни разу не ссылаются на `AcraMailImporter`/
`AcraNewsImporter`/`NraImporter` и не зависят от того, как именно
рождаются `events` — только читают их. Проверено: оба офлайн-теста
(`test_bot_ux_screens.php` — 73 проверки, `test_notification_dispatcher.php`
— 27 проверок) проходят на реальном коде без единой правки логики.
Найдено и исправлено при слиянии:

1. **Коллизия номера миграции.** Присланная `018_bot_ux_tariff_and_
   dialog_state.sql` конфликтовала с уже применённой в проде
   `018_outlook_under_review.sql` (этап 3, ENUM `under_review`/
   `review_concluded`) — переномерована в `019_...`.
2. **Файл `.gitignore` не содержал `config/telegram_bot.php`.** Добавлен
   — иначе реальный токен бота рисковал попасть в git при первом же
   `git add` после создания файла из `.example`.
3. **Две ссылки на несуществующий `config/acra_mailbox.php`/
   `AcraMailboxConfig`** (в докблоках `TelegramBotConfig`/
   `telegram_bot.example.php`, "тот же принцип, что у config/
   acra_mailbox.php") — тот же класс, что не понадобился в Фазе 1
   (см. выше): в основной ветке ACRA идёт через `AcraNewsImporter`,
   почтовый импортёр так и не был построен. Ссылки убраны, сам принцип
   (секрет отдельно от кода) описан без привязки к несуществующему
   файлу.

Найдено ПОСЛЕ мержа, на первом живом прогоне на бою (10 сентября 2026,
пользователь тестировал «Выбор эмитентов» вживую через реального бота):

4. **`BotCommandHandler::searchIssuers()` падал на поиске по фрагменту
   названия** — `SQLSTATE[HY093]: Invalid parameter number` в логе демона
   на каждый свободный текстовый поиск. Причина: SQL-запрос
   (`WHERE short_name LIKE :fragment OR full_name LIKE :fragment`)
   использовал ОДНО именованное :имя ДВАЖДЫ, а `execute()` передавал под
   него только одно значение. `Database::connection()` держит
   `PDO::ATTR_EMULATE_PREPARES=false` (настоящие подготовленные запросы
   MySQL) — в этом режиме каждое ВХОЖДЕНИЕ плейсхолдера требует своего
   значения, даже при одинаковом имени. Под SQLite (офлайн-тесты) такого
   ограничения нет — оно нативно допускает повтор одного :имени — поэтому
   `test_bot_ux_screens.php` (в котором ЕСТЬ прямая проверка
   `searchIssuers()` по фрагменту "нефт") этот баг не поймал: тот же
   класс пробела, что MySQL-диалект `ON DUPLICATE KEY UPDATE` в Фазе 1 —
   SQLite просто не воспроизводит конкретное ограничение MySQL, которое
   тут сработало. Исправлено: два разных плейсхолдера (`:fragment1`/
   `:fragment2`), `execute()` передаёт значение под каждым.
   Добавлен `tests/test_no_duplicate_named_params.php` — статическая
   проверка (без БД вообще, просто чтение текста запросов), сканирует
   все `->prepare()` в `src/`+`bin/` на повтор `:имени` в одном запросе —
   ловит именно этот класс бага навсегда, а не только этот конкретный
   случай.

## Доработки 17 сентября 2026 (по итогам живой эксплуатации)

Четыре отдельных запроса пользователя после первых дней работы бота на
проде — все реализованы вместе, т.к. первые два касаются одного и того
же участка (`FnsBlocksImporter`/`EventPublisher`/`NotificationDispatcher`):

1. **Повторные попытки при ошибке ФНС.** Раньше неудачная проверка
   (капча/сеть) ждала следующего ежедневного крона — до суток. Теперь
   `FnsBlocksImporter::checkIssuers()` делает до `$maxRetries`
   дополнительных проходов (по умолчанию 2, пауза 90 с) ТОЛЬКО по
   эмитентам, не прошедшим проверку — `bin/check_fns_blocks.php` даёт
   `--retries`/`--retry-delay` для настройки, `--retries=0` — старое
   поведение. Суточный крон остаётся финальной страховкой.
2. **Баг: новый подписчик получал ВЕСЬ исторический бэклог событий
   эмитента.** `NotificationDispatcher::fetchPendingPairs()` выбирала
   ЛЮБОЕ событие эмитента, для которого ещё нет строки в `notifications`
   у конкретного (user, event) — а для только что добавленного в
   watchlist эмитента такой строки не было ни у одного ИЗ ВСЕХ его
   прошлых событий, накопленных другими прогонами задолго до этого
   пользователя. Живой пример — при добавлении ООО «КОНТРОЛ лизинг»
   пользователь получил 4 сообщения разом (2 старых "заблокировано" с
   разными суммами + 2 старых "снято" с разными датами). Исправлено:
   `JOIN watchlist w ON w.issuer_id = e.issuer_id AND w.added_at <=
   e.detected_at` — пользователь видит только события, случившиеся ПОСЛЕ
   того, как он сам начал следить. И `watchlist.added_at`, и
   `events.detected_at` уже существовали в схеме с самого начала —
   миграция не понадобилась.
3. **Четвёртый триггер E1 — `count_changed`.** См. выше, раздел про
   триггеры E1 и обновлённые шаблоны сообщений.
4. **Разовая проверка ФНС сразу при добавлении эмитента.** Раньше
   "Статус" по только что добавленному эмитенту молчал, пока хотя бы
   одна плановая проверка не случится (до суток), а если блокировка уже
   была известна СИСТЕМЕ (не новая, просто пользователь новый) — новый
   подписчик вообще не узнавал о ней через `events` (E1 создаётся только
   при РЕАЛЬНОМ изменении состояния эмитента, а не по факту чьей-то новой
   подписки). Добавлено: `BotCommandHandler::checkFnsOnAdd()` — при
   успешном добавлении в watchlist (`toggleIssuer()`/`pickIssuer()`)
   синхронно проверяет ФНС для этого ОДНОГО эмитента (не хуже полного
   прогона по нагрузке — одно действие пользователя = одна проверка), не
   дублируя проверку, если она уже была недавней и успешной
   (`isFnsCheckFresh()`, порог `FNS_ON_ADD_FRESH_HOURS`=12 — экономим
   запросы к и так капчащему service.nalog.ru). Результат отправляется
   НАПРЯМУЮ этому пользователю (`sendMessage`, не через `events`/
   `notifications` — тот путь общий для всех подписчиков и не должен
   сработать только из-за новой подписки), и ТОЛЬКО если блокировка
   реально есть — молчание при её отсутствии осознанное (прямое решение
   пользователя). Текст — тот же формат, что у `kind='started'`.

## Дальше, не сейчас (осознанно вне этого MVP)

- Платежи/апгрейд тарифа за лимитом free (сейчас — просто отказ
  добавить в watchlist сверх лимита, без покупки).
- `E3` "Каскад по эмитенту" — производный тип, требует корреляции
  нескольких `events` одного эмитента (например, понижение рейтинга +
  блокировка ФНС почти одновременно = отдельное усиленное
  уведомление) — осмысленная будущая надстройка, не MVP.
- НРД/e-disclosure источники (группы A/B/D целиком) — по прямому
  решению пользователя, не в этом заходе.
- Веб-канал уведомлений (`notifications.channel='web'`) — только
  `telegram` в MVP.
- Точная эскалация приоритета по силе действия (например, отзыв
  рейтинга — `red`, а не дефолтный `yellow` у C5) — MVP использует
  `event_types.default_priority` как есть, без событие-специфичных
  правок.

# BondKeeper — этап 1: БД + сидирование бесплатными данными

Реализация первого этапа дорожной карты:
1. Создать БД.
2. Заполнить справочные таблицы бесплатными данными (ISS API Мосбиржи), без платных источников (НРД, e-disclosure).
3. Понять, что из схемы (`documents/2026.08.08_BondKeeper_Schema_Reference.pdf`, `documents/2026.08.08_bondkeeper_schema_v2.sql`) вообще можно бесплатно вытащить.

Пошаговая инструкция по разворачиванию на боевом сервере (ISPmanager, домен уже создан) и по тестированию первого прогона — `docs/DEPLOY_STAGE1.md`.

## Стек

PHP 8.3+ (CLI, `pdo_mysql`, `curl`), MySQL 8.0+, cron. Без composer/фреймворка — намеренно: `bin/*.php` должны запускаться на обычном shared-хостинге (см. скриншот конфигурации ПО) через `php bin/seed_market.php` без шага установки зависимостей.

## Структура

```
database/001_schema.sql   — схема БД (см. "Изменения относительно v2" ниже)
src/Database.php          — подключение к MySQL (PDO)
src/Iss/IssClient.php     — HTTP-клиент ISS API Мосбиржи
src/Iss/SecuritiesImporter.php   — issuers/securities/redemptions(scheduled_maturity)
src/Iss/BondizationImporter.php  — coupons/amortizations
bin/seed_market.php       — запуск сидирования справочника (шаг 1)
bin/seed_bondization.php  — запуск сидирования графика выплат (шаг 2)
```

## Запуск

```bash
cp .env.example .env   # прописать реальные DB_* значения
mysql -u root -p -e "CREATE DATABASE bondkeeper CHARACTER SET utf8mb4 COLLATE utf8mb4_unicode_ci;"
mysql -u root -p bondkeeper < database/001_schema.sql

php bin/seed_market.php        # issuers, securities, redemptions(scheduled_maturity)
php bin/seed_bondization.php   # coupons, amortizations
```

По расписанию — раз в сутки (справочник меняется редко, см. `documents/2026.08.08_Seeding_And_Polling_Strategy_QA.docx` про частоту опроса): cron-примеры даны в шапке каждого `bin/*.php`.

## Изменения относительно `bondkeeper_schema_v2.sql`

Схема была впервые реально развёрнута (а не только рецензирована построчно) в рамках этого этапа — на настоящем MySQL 8.0.46. Два расхождения с распечаткой v2, найденные только при фактическом `CREATE`/`ALTER`, а не при чтении SQL:

1. **`event_stories.chk_event_stories_exactly_one` убран.** MySQL 8 отклоняет `CHECK` на колонке, у которой есть `FOREIGN KEY ... ON DELETE SET NULL` (ошибка 3823) — сервер не может гарантировать, что каскадный `SET NULL` не нарушит условие задним числом. Правило "ровно одно из `coupon_id`/`amortization_id`/`redemption_id` заполнено" переносится в код классификатора событий (единственное место, создающее строки в этой таблице, — задача следующего этапа).
2. **`watchlist`: FK на `issuer_id`/`security_id` вынесены в отдельный `ALTER TABLE`, `ON DELETE CASCADE` → `RESTRICT`.** `issuer_id` и `security_id` — базовые столбцы генерируемой колонки `issuer_only_key`. MySQL 8 официально запрещает `CASCADE`/`SET NULL`/`SET DEFAULT` как referential action на таких столбцах (ошибка 3192, MySQL Reference Manual §13.1.20.8) и отдельно не позволяет объявить такой FK в одной инструкции с `CREATE TABLE`, где эта generated-колонка определена (ошибка 1215). На практике `issuers`/`securities` физически не удаляются (см. `status`-поле в `securities`), так что `RESTRICT` ничего не меняет по сути — просто корректно проходит на реальном сервере.

Остальные 18 таблиц, таксономия событий (24 типа) и тарифы применились без изменений — полный лог `database/001_schema.sql` воспроизводит первоисточник `bondkeeper_schema_v2.sql` за вычетом этих двух правок.

## Как это было проверено

В этой рабочей среде нет исходящего доступа в интернет (сетевая политика окружения блокирует произвольные HTTP-запросы, включая `iss.moex.com`) — поэтому импортёры **не были прогнаны против настоящего ISS API**. Вместо этого проверено следующее, на реальном MySQL 8.0.46, поднятом локально:

- Полное применение `database/001_schema.sql` с нуля, включая все FK, `CHECK`, генерируемые колонки и seed-данные (`event_types` — 24 строки, `tariffs` — 4 строки).
- Весь путь записи `SecuritiesImporter`/`BondizationImporter` — против тестового двойника `IssClient` с фикстурами, повторяющими документированную форму ответа ISS API (`{"columns": [...], "data": [[...]]}` — блоки `description`, `boards`, `coupons`, `amortizations`). Проверены: upsert эмитента/бумаги, идемпотентность повторного запуска, пересчёт `redemptions.value_per_bond` при наличии амортизации, и — намеренно — случай, когда ИНН эмитента не резолвится (бумага пропускается, а не записывается с выдуманным ИНН).
- `php -l` на все файлы.

Что это означает практически: **структура схемы и логика записи в БД проверены по-настоящему**, но **точные имена полей/эндпоинтов ISS API — нет**. Разворачивая на боевом хостинге (где есть интернет), первый прогон `seed_market.php` может потребовать поправить имена полей в `SecuritiesImporter::resolveOrCreateIssuer()`/`upsertSecurity()` и путь discovery-эндпоинта под фактический ответ API — код написан так, чтобы это были точечные правки, а не переписывание логики.

## Что бесплатно (ISS API), а что нет — ответ на пункт 3 дорожной карты

Подтверждено предыдущим исследованием (`documents/2026.08.01_ProfitBonds_NSD_eDisclosure_Event_Taxonomy_QA.docx`, `documents/2026.08.08_Schema_Design_Walkthrough_QA.docx`) и воспроизведено в структуре импортёров:

**Точно бесплатно, без авторизации, через ISS API:**
ISIN, SECID, краткое/полное наименование бумаги, номинал, валюта, дата погашения, дата ближайшей оферты (`BUYBACKDATE`), объём выпуска, уровень листинга, весь график купонов и амортизаций (bondization-эндпоинт), НКД и доходность *на сегодня* (не на произвольную дату).

**Требует ручного расчёта поверх бесплатных данных (не отдельное поле):**
НКД на произвольную дату (считается по графику купонов), `full_default_date_planned` (плановая дата полного дефолта — считается сами: `period_end_date` + 10 рабочих дней по производственному календарю), доходность к оферте отдельно от доходности к погашению (не подтверждено, что ISS отдаёт обе одновременно).

**Не подтверждено / вероятно недоступно бесплатно и структурированно** — реализовано как явный пропуск с логированием, а не как угадывание:
- **ИНН эмитента по бумаге** — самый важный пробел. Блок `description` конкретной бумаги — это данные о *бумаге*, а не структурированная карточка эмитента как юрлица; способ надёжно связать ISIN с ИНН через бесплатный ISS API не был подтверждён в первоисточнике (`cci/info/companies` разбирался как отдельный, не до конца проверенный вопрос доступа). `SecuritiesImporter` пробует несколько правдоподобных алиасов поля и **пропускает бумагу**, если ИНН не резолвится, — это единственный безопасный выбор для сервиса, который дальше сверяет ФНС/e-disclosure по этому же ключу: придуманный ИНН опаснее отсутствующего.
- Вид оферты (put/call) — по независимому подтверждению в первоисточнике не отдаётся явным полем ISS API.
- `is_instruction_based` (поинструкционный расчёт по оферте) — не проверено, какое поле НРД это отражает.
- `coupon_type`/`is_subordinated`/`is_structured`/`is_qualified_investors_only` — в первоисточнике прямо указано, что определяются «по косвенным признакам, не всегда точно»; в коде оставлены как значения по умолчанию из схемы, а не выводятся автоматически.

Практический вывод: справочник **бумаг и графика выплат** (кластер 1 почти целиком) сидируется бесплатно и автоматически. Связка **бумага → эмитент-юрлицо с ИНН** и горстка риск-флагов бумаги — узкое место, которое, по всей видимости, требует либо ручного обогащения, либо платного источника (Cbonds), либо парсинга эмиссионной документации — это открытый вопрос для следующей итерации, а не решённая часть этапа 1.
